# قالب عمومی «بیلدر پیوسته» — راهنمای استفاده

> فایل کپی‌شونده: [`UNIVERSAL-BUILDER-TEMPLATE-COPY.txt`](UNIVERSAL-BUILDER-TEMPLATE-COPY.txt)
> خلاصه‌شده از همان پرامپتی که در Muscle Paradise کار کرد، ولی عمومی و بدون وابستگی به آن پروژه.

---

## چرا نسخهٔ MP کار کرد؟ (و چه چیزی را باید حفظ کنی)

پنج مکانیزم، نه بیشتر. اگر این پنج را داشته باشی، برای هر پروژه‌ای جواب می‌دهد:

| مکانیزم | چه مشکلی را حل می‌کند |
|---|---|
| **مجوز ایستا** | AI بعد از هر کار نمی‌پرسد «ادامه بدهم؟» — اختیار از قبل داده شده |
| **الگوریتم انتخاب کار بعدی** | AI لازم نیست حدس بزند؛ ترتیب از منبع خوانده می‌شود |
| **STATE_FILE** روی ریموت | با قطع‌شدن نشست، کار از بین نمی‌رود و از جای درست ادامه می‌دهد |
| **DoD + قالب شاهد** | جلوی «PASS بدون اجرا» و «۹٬۰۰۰ خط سند، صفر خط کد» را می‌گیرد |
| **شرایط توقف محدود** | فقط چهار حالت مجاز به توقف؛ بقیه ⇒ ادامه با کار مستقل بعدی |

بقیهٔ متن فقط جزئیات این پنج است.

## چطور برای یک پروژهٔ جدید استفاده کنی (۵ دقیقه)

### ۱. CONFIG را پر کن
یک‌بار برای هر پروژه. اگر چیزی را نمی‌دانی، خالی بگذار — AI باید بپرسد یا BLOCKED بزند، نه حدس.

```text
PROJECT:            فروشگاه کتاب «کتابخانه»
REPO_OR_WORKSPACE:  user/bookstore
BRANCH:             arena/<session>-bookstore
BASE_BRANCH:        main
STACK:              Next.js 14 + Postgres + Prisma
SOURCE_OF_TRUTH:    docs/ROADMAP.md (بخش «فاز ۲») + issues باز با برچسب p1
STATE_FILE:         docs/BUILD-STATE.md
SCOPE:              همهٔ آیتم‌های فاز ۲
EVIDENCE_DIR:       evidence/{{تاریخ}}/{{ID}}/
AUTONOMY:           LOCAL_BUILD_COMMIT_PUSH
GATES:              npm run lint
                    npm run build
                    npm test
                    npx prisma validate
PROTECTED:          prisma/migrations/**, .env*, payments/**
OWNER_ONLY:         انتخاب درگاه پرداخت، قیمت‌گذاری، انتشار، حذف داده
REPORT_LANG:        fa
```

### ۲. STATE را از قبل بساز (توصیهٔ مهم)
اگر STATE_FILE وجود نداشته باشد، AI خودش می‌سازد — ولی بهتر است تو با ۳ خط شروع کنی:

```markdown
| ترتیب | ID | وضعیت | شاهد | اقدام بعدی دقیق |
|---|---|---|---|---|
| 1 | P2-01 | TODO | — | اسکیمای سبد خرید + تست |
| 2 | P2-02 | TODO | — | صفحهٔ پرداخت (mock gateway) |
```

### ۳. یک کار را برای شروع بده
AI بهتر است از یک لنگر مشخص شروع کند، نه از صفر مطلق:

```text
اول P2-01 را انجام بده و بعد همان‌طور که متن می‌گوید ادامه بده.
```

## سه قانونی که بیشترین ارزش را داشتند (و اغلب از قلم می‌افتند)

### ۱) PUSH-OR-IT-DIDN'T-HAPPEN
اگر کار روی ریموت نباشد، وجود ندارد. این تک‌خط جلوی ۹۰٪ «کار از دست رفت» را می‌گیرد.
در MP، یک نشست کامل crosswalk ساخت و push نکرد — و همه‌اش رفت.

### ۲) «ابزار موجود نیست» دلیل پذیرفته‌شده نیست
در MP، بیلدر یازده کارت را با «Chromium در sandbox نیست» بست. بعد معلوم شد همان پروژه
قبلاً با `@sparticuz/chromium` روی همان سندباکس تست کرده بود. پس قالب می‌گوید:

> ابتدا نسخهٔ OSS/registry را امتحان کن. اگر واقعاً شکست خورد، **خطای دقیق** را بنویس.
> «موجود نیست» فرض است؛ «`libnspr4.so` پیدا نشد» شاهد است.

### ۳) هر چرخه یک تغییر کد یا تست
بدون این قانون، حلقه به «اسنادسازی پیوسته» تبدیل می‌شود. در MP: ۱۱ commit، ۹٬۴۹۱ خط
evidence، صفر خط کد — و ۹۷ checkbox هنوز باز. قالب می‌گوید دو چرخهٔ متوالی بدون کد
مجاز نیست، سومی `LOOP_STALLED=yes`.

## چه چیزی را عمداً در قالب نگذاشتم

| چیز | چرا |
|---|---|
| ساختار پروژه، مسیر فایل‌ها، نام endpoint | مخصوص MP بود؛ در CONFIG می‌آید |
| تصمیم‌های محصول (ADR، scope قفل‌شده) | در `SOURCE_OF_TRUTH` و `PROTECTED` می‌آید |
| دستورهای تست مخصوص | در `GATES` می‌آید |
| قواعد زبان/فرمت کد | از `CONTRIBUTING` یا `AGENTS.md` پروژه خوانده می‌شود |
| «PR بساز» به‌عنوان کار اجباری | در بعضی محیط‌ها مجوز نیست؛ به `gh pr create` با fallback اشاره شده |

## اگر محیط محدود است (بدون دسترسی push)

بعضی سندباکس‌ها یا نشست‌ها اجازهٔ push نمی‌دهند. در این حالت:

1. `AUTONOMY: LOCAL_ONLY` بگذار.
2. `EVIDENCE_DIR` را داخل workspace نگه دار (نه `/tmp`) تا در snapshot بماند.
3. در STATE خط `PUSHED: blocked_by_environment` بنویس — نه اینکه وانمود کنی push شد.
4. گزارش پایان را طوری بنویس که مالک بتواند همان دستورها را دستی اجرا کند.

---

## چطور تشخیص بدهی قالب دارد کار می‌کند (نه اینکه فقط خوش‌ظاهر است)

بعد از دو سه چرخه، این چهار نشانه را ببین:

- [ ] در STATE، ردیف‌های بالایی وضعیتشان عوض شده — نه فقط فایل جدید اضافه شده.
- [ ] `CODE_CHANGED` در گزارش‌ها پر است، نه «هیچ».
- [ ] `claimed_sha` با `tested_sha` یکی است.
- [ ] هر «DONE» یک دستور + عدد کنارش دارد.

اگر یکی از این‌ها نبود، قالب را دوباره نفرست — **آن بند مشخص** را تقویت کن.
مثلاً اگر `CODE_CHANGED` خالی است، بند ۱۲ را با جریمهٔ صریح‌تر بفرست.

## نسخهٔ کوتاه (برای پروژه‌های کوچک)

اگر پروژه کوچک است و ۱۷۶ خط زیادی است، این ۱۲ خط کافی است:

```text
تو بیلدر این پروژه‌ای. مجوز ایستا داری: بدون پرسیدن، کارهای محلی و برگشت‌پذیر
را انجام بده، commit کن و به شاخهٔ <BRANCH> push کن. مرجع کار: <SOURCE_OF_TRUTH>.
وضعیت را در <STATE_FILE> نگه دار و قبل از پایان نوبت push کن.

قواعد سخت:
۱ کار تا push نشود تمام نیست.
۲ هر چرخه یک تغییر کد یا تست + یک شاهد با دستور و عدد.
۳ merged_sha = tested_sha؛ وگرنه NOT_RUN.
۴ روی main مستقیم commit نکن؛ force/reset/clean ممنوع.
۵ تصمیم مالک (پول/انتشار/حقوقی/دادهٔ واقعی) = BLOCKED، برو کار بعدی.
۶ توقف فقط وقتی SCOPE تمام یا مسدود شده باشد.

هر بار: git fetch → وضعیت → NEXT → پیاده‌سازی+تست → GATES → شاهد → commit/push.
گزارش: DONE / CODE_CHANGED / گیت‌ها / NEXT / BLOCKED / PUSHED
```

## ذخیره برای استفادهٔ بعدی

`UNIVERSAL-BUILDER-TEMPLATE-COPY.txt` را در یک ریپوی شخصی (مثلاً `me/prompts`) بگذار و
هر بار فقط CONFIG را عوض کن. با این کار:
- نسخهٔ تاریخ‌دار داری و می‌دانی کدام نسخه کار کرد.
- می‌توانی بین پروژه‌ها مقایسه کنی کدام بند مؤثر بود.
- دیگر لازم نیست هر بار از صفر پرامپت بنویسی.
