# ۰۱ — پروتکل لوپ اجرایی
## قلب تپندهٔ واگذاری به عامل · MP-LOOP v1.0

> این سند **رفتار** عامل را تعریف می‌کند، نه محتوای کار را.
> در **هر** تسک، بدون استثنا، همین ۹ گام تکرار می‌شود.

# ۱. چرخهٔ ۹ گامی

```
      ┌──────────────────────────────────────────────┐
      │                                              │
      ▼                                              │
  ①  PICK    یک تسک READY از TASK_BOARD               │
      ▼                                              │
  ②  READ    سند لوپ + فایل‌های مرجع                  │
      ▼                                              │
  ③  PLAN    نوشتن نقشه در ۳ تا ۷ خط                  │

      ▼                                              │

      ▼                                              │
  ⑥  VERIFY  اجرای دستور verify تسک                   │

    سبز؟ ──خیر──► ⑦ HEAL (حداکثر ۳ بار) ──────────────┤
      │ بله                                          │
      ▼                                              │
  ⑧  GATE    اجرای ۵ دروازهٔ کیفیت                    │
      ▼                                              │

```

# ۲. شرح گام‌ها

## ① PICK — انتخاب تسک

```
قانون ۱: فقط تسک با وضعیت READY.
قانون ۲: فقط یکی در هر زمان. هرگز دو تسک باز نکنید.
قانون ۳: به ترتیب شمارهٔ تسک در لوپ، مگر اینکه صریحاً موازی علامت خورده باشد.
قانون ۴: اگر همهٔ تسک‌های لوپ فعلی DONE شدند، معیار خروج لوپ را بسنجید،
         سپس به لوپ بعدی بروید.
```
وضعیت تسک را فوراً به `IN_PROGRESS` تغییر دهید و در `TASK_BOARD.md` ثبت کنید.

## ② READ — خواندن زمینه

قبل از نوشتن حتی یک خط کد:
- سند لوپ آن تسک را بخوانید؛
- فایل‌های ذکرشده در ستون «فایل‌ها» را **واقعاً باز کنید و بخوانید**؛
- سند مرجع در `../build/` را که تسک به آن ارجاع می‌دهد بخوانید.

> ⚠️ **رایج‌ترین خطای عامل‌ها:** حدس زدن محتوای فایل به‌جای خواندنش.
> اگر فایل را نخوانده‌اید، کدی که می‌نویسید حدس است، نه مهندسی.

## ③ PLAN — نقشهٔ کوتاه

۳ تا ۷ خط بنویسید:
```
هدف:        [یک جمله]
فایل‌ها:     [فهرست دقیق فایل‌هایی که لمس می‌شوند]
تست:        [نام تستی که می‌نویسم و چه چیزی را اثبات می‌کند]
ریسک:       [چه چیزی ممکن است بشکند]
```
اگر نقشه بیش از ۷ خط شد، **تسک بیش از حد بزرگ است** — آن را بشکنید و در
`TASK_BOARD.md` به‌عنوان دو تسک ثبت کنید.

## ④ TEST — اول تست، همیشه

**تست را قبل از کد بنویسید و مطمئن شوید قرمز است.**

```bash
# اجرا کنید و ببینید شکست می‌خورد
pytest tests/test_x.py::test_new -x
# انتظار: FAILED
```

> اگر تست بدون نوشتن کد **سبز** شد، تست شما چیزی را نمی‌سنجد. دوباره بنویسید.

### سه قانون آهنین تست
| # | قانون | چرا |
|---|---|---|
| T1 | **هرگز به ساعت واقعی وابسته نباشید** | `vi.useFakeTimers()` / `freezegun`. این پروژه یک بار قربانی شد |
| T2 | **هرگز به منطقهٔ زمانی وابسته نباشید** | با تقویم جلالی، `TZ=Pacific/Kiritimati` را هم بسنجید |
| T3 | **هرگز به شبکه وابسته نباشید** | mock کنید |

## ⑤ BUILD — کمترین کد

فقط آن‌قدر کد بنویسید که تست سبز شود. نه بیشتر.

**ممنوعیت‌ها:**
- ❌ افزودن وابستگی بدون پر کردن فرم بخش ۶
- ❌ تغییر فایلی که در نقشه نبود
- ❌ «بهینه‌سازی» کدی که تسک به آن ربط ندارد
- ❌ تغییر `ce-app/` یا `docs/CuttingEdge/`

## ⑥ VERIFY — اجرای دستور تسک

هر تسک یک ستون `verify` دارد با یک دستور دقیق. اجرا کنید.

```
exit 0  → گام ⑧
غیر ۰   → گام ⑦
```

## ⑦ HEAL — خود-ترمیمی (حداکثر ۳ تلاش)

این مهم‌ترین بخش پروتکل است. **کورکورانه چیز عوض نکنید.**

```
تلاش ۱ — تشخیص
  □ پیام خطا را کامل بخوانید (نه فقط خط آخر)
  □ کدام فایل؟ کدام خط؟ چه چیزی انتظار می‌رفت و چه شد؟
  □ فرضیه بنویسید: «فکر می‌کنم علت X است چون Y»
  □ فرضیه را با یک تغییر کوچک بسنجید

تلاش ۲ — دامنه را محدود کنید
  □ کوچک‌ترین ورودی که خطا را بازتولید می‌کند چیست؟
  □ آیا آخرین تغییر شما باعثش شد؟ (git diff)
  □ آیا فرض شما دربارهٔ یک API غلط بود؟ مستند را بخوانید

تلاش ۳ — عقب‌نشینی
  □ git stash — آیا بدون تغییرات شما سبز است؟
  □ اگر بله: تغییر شما مقصر است، رویکرد را عوض کنید
  □ اگر خیر: مشکل از قبل بوده — تسک جدید بسازید و ثبت کنید
```

### اگر بعد از ۳ تلاش هنوز قرمز است — **توقف**

```
۱. تغییرات را برگردانید: git checkout -- <files>
۲. تسک را BLOCKED کنید در TASK_BOARD.md
۳. در ERRORS.log ثبت کنید:
     - تاریخ · شناسهٔ تسک
     - چه کاری می‌کردید
     - پیام خطای کامل
     - سه فرضیه‌ای که سنجیدید و چرا رد شدند
     - چه چیزی برای رفع لازم است
۴. به تسک بعدی بروید.
```

> **هرگز**: تست را حذف نکنید تا سبز شود. `--no-verify` نزنید. آستانهٔ پوشش را
> پایین نیاورید. تست را `skip` نکنید. اینها تقلب‌اند، نه رفع اشکال.

## ⑧ GATE — پنج دروازه

```bash
# G1 بک‌اند
cd mp-app/backend && pytest --override-ini="addopts=" -q --cov=app --cov-fail-under=85

# G2 فرانت
cd mp-app/studio && npm run gate

# G3 امنیت
bandit -q -c mp-app/backend/bandit.yaml -r mp-app/backend/app -ll

# G4 همگامی اسپک (اگر API لمس شد)
cd mp-app/backend && python -m app.export_openapi --yaml > /tmp/o.yaml && diff ../openapi.yaml /tmp/o.yaml

# G5 معماری
! grep -rl "^from fastapi\|^import fastapi" mp-app/backend/app/core/
! grep -rl "^from sqlalchemy\|^import sqlalchemy" mp-app/backend/app/routers/
```
**هر پنج باید exit 0 بدهند.** یکی قرمز = برگرد به ⑦.

## ⑨ COMMIT — ثبت و به‌روزرسانی

```bash
git add -A
git commit -m "<type>(<loop>): <خلاصه>

<چرا این تغییر لازم بود — نه اینکه چه کرد>

Task: <TASK-ID>
Verify: <دستور> → exit 0
Measured: <عدد قبل> → <عدد بعد>"
```

سپس **حتماً**:
- `TASK_BOARD.md` → وضعیت تسک = `DONE` + تاریخ + عدد اندازه‌گیری‌شده
- `mp-app/CHANGELOG.md` → اگر رفتار کاربر عوض شد

# ۳. جدول خطاهای رایج و رفع سریع

| نشانه | علت محتمل | رفع |
|---|---|---|
| تست دیروز سبز، امروز قرمز | تاریخ هارد-کد | ساعت را فریز کنید (T1) |
| در CI قرمز، محلی سبز | منطقهٔ زمانی یا نصب تازه | `TZ=...` بسنجید؛ در venv خالی نصب کنید |
| `SQLITE_BUSY` | `busy_timeout` نبود | ✅ رفع شده — اگر برگشت، `db.py` را ببینید |
| `diff openapi.yaml` قرمز | مسیر اضافه شد، اسپک نه | `python -m app.export_openapi --yaml > ../openapi.yaml` |
| پوشش زیر ۸۵٪ | شاخهٔ خطا تست ندارد | تست حالت خطا بنویسید، نه حالت خوشحال بیشتر |
| `bandit` قرمز | یافتهٔ جدید | رفع کنید؛ اگر مثبت کاذب است، در `bandit.yaml` **با دلیل مکتوب** |
| `eslint` قرمز | `--max-warnings=0` | رفع کنید؛ `eslint-disable` فقط با کامنت دلیل |
| import چرخه‌ای | لایه معکوس شد | C13 را ببینید |

# ۴. معیار خروج لوپ

وقتی همهٔ تسک‌های یک لوپ `DONE` شدند، **قبل از رفتن به لوپ بعد**:

```
□ همهٔ تسک‌ها DONE یا BLOCKED با دلیل مکتوب
□ هر ۵ دروازه سبز
□ معیار خروج مخصوص آن لوپ (در انتهای سند لوپ) برقرار است
□ CHANGELOG یک ورودی با عدد اندازه‌گیری‌شده دارد
□ خلاصهٔ لوپ در TASK_BOARD.md نوشته شده:
    - چند تسک انجام شد
    - کدام اعداد جابه‌جا شدند (قبل → بعد)
    - چه چیزی BLOCKED ماند و چرا
```

# ۵. پروتکل بازنگری (Self-Review)

**هر ۵ تسک**، قبل از ادامه، این ۷ سؤال را از خودتان بپرسید و جواب را بنویسید:

```
۱. آیا کدی نوشتم که هیچ تستی آن را نمی‌سنجد؟
۲. آیا جایی «موقتاً» چیزی گذاشتم که فراموش می‌شود؟ (TODO/FIXME بشمارید)
۳. آیا وابستگی جدیدی اضافه کردم؟ فرم بخش ۶ را پر کردم؟
۴. آیا عددی که در CHANGELOG نوشتم واقعاً اندازه گرفتم یا تخمین زدم؟
۵. آیا لایه‌بندی را جایی نقض کردم؟
۶. آیا رشتهٔ فارسی هارد-کد اضافه کردم که باید در i18n باشد؟
۷. آیا چیزی نوشتم که فقط روی ماشین من کار می‌کند؟
```

اگر جواب هرکدام «بله» بود، **یک تسک اصلاحی بسازید** و قبل از ادامه انجامش دهید.

# ۶. فرم افزودن وابستگی

هیچ `pip install` یا `npm i` بدون پر کردن این فرم در پیام commit:

```
نام بسته:
لایه:                    A (ابزار توسعه) یا B (داخل محصول)
مجوز:                    ← اگر GPL/AGPL و لایه B: رد خودکار
حجم افزوده (gzip):        ← اگر > 20kB و لایه B: توجیه لازم
آفلاین کار می‌کند؟         ← اگر خیر و لایه B: رد
چه چیزی را حذف می‌کند؟     ← اگر «هیچ»: احتمالاً لازم نیست
جایگزین دست‌ساز چند خط؟    ← اگر < 100 خط: خودتان بنویسید
```
و افزودن به `mp-app/NOTICES.md`.

# ۸. ده قانونی که هرگز نقض نمی‌شوند

```
۱.  ce-app/ و docs/CuttingEdge/ را دست نزنید
۲.  تست را برای سبز شدن حذف یا skip نکنید
۳.  آستانهٔ پوشش را پایین نیاورید
۴.  --no-verify یا --force نزنید
۵.  بیش از یک تسک هم‌زمان باز نکنید
۶.  عددی که اندازه نگرفته‌اید ننویسید
۷.  وابستگی GPL/AGPL به محصول اضافه نکنید
۸.  راز (کلید، رمز، توکن) در گیت ننویسید
۹.  بعد از ۳ تلاش ناموفق، BLOCKED کنید — نه تلاش چهارم کورکورانه
۱۰. اگر شک دارید که کاری امن است یا نه، **محافظه‌کارانه‌ترین گزینه** را بردارید
```
