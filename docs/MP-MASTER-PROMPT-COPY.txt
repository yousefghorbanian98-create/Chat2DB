۰) قانون سخت (سه خط)

۴) مرور دستی که اسکریپت نمی‌تواند انجام دهد

۱۰) توقف فقط در این چهار حالت
   (الف) همهٔ کارهای بخش ۱ tracker بسته یا BLOCKED/UNKNOWNِ مستند شده‌اند
         → گزارش «پایان صف محلی» + فهرست بلاکرها + پرسش‌های مالک (هر کدام یک خط).
   (ب) مالک صریحاً «توقف» بدهد.
   (ج) کار بعدی فقط با تصمیم برگشت‌ناپذیر/خارج از scope جلو می‌رود.
   (د) محدودیت سخت محیط بدون جایگزین (فقط همان item را متوقف می‌کند، نه حلقه).
   در همهٔ حالت‌ها قبل از پایان، STATE را طوری بنویس که «ادامه» از جای درست شروع شود.

۱۱) قالب گزارش پایان چرخه (کوتاه)
   DONE: <IDها> | وضعیت: از X به Y | شاهد: <دستور + نتیجهٔ عددی>
   DIFF: <فایل‌های اصلی>
   گیت‌ها: lint/build/test/docs → pass/fail
   NEXT: <ID بعدی> — چرا
   BLOCKED: <IDs + یک خط>
   PUSHED: <sha> روی <branch>  ← اگر این خط خالی است، کار تمام نشده

۷) چرخهٔ اجرا (هفت گام، هر بار)

5. اجرای گیت‌های بند ۸ با دستور واقعی؛ خروجی خام را نگه دار.
6. ثبت شاهد طبق بند ۱۰؛ به‌روزرسانی ردیف tracker با وضعیت واقعی؛ STATE و بخش جاری HANDOFF.
7. commit و push در چک‌پوینت‌ها (بدون push، شاهد رسمی نیست) و بی‌درنگ گام ۲ بعدی در همان نوبت.

۸) گیت‌های واقعی (از ریشهٔ مخزن؛ نسخه‌ها را در evidence بنویس)
- Studio: cd mp-app/studio && npm ci && npm run lint && npm run build
  تست کامل از سقف زمان می‌گذرد → shard کن: npm test -- --shard=1/3 ، 2/3 ، 3/3.
- Backend: python -m venv .venv && . .venv/bin/activate && python -m pip install -e "mp-app/backend[dev]"
  سپس cd mp-app/backend && python -m pytest (کامل حدود ۲۰۰ ثانیه؛ در حین کار تست هدفمند همان حوزه).
  ruff check و ruff format --check .
  اگر coverage_run.sh با خطای env شکست خورد، PASS ننویس.
- Docs: python3 scripts/docs_gate.py ، python3 scripts/assemble_project_guide.py --check ،
  python3 scripts/interaction_map.py --check ، python3 scripts/repo_hygiene_gate.py ،
  cd tools/mermaid-check && npm ci && node check.mjs ، git diff --check.
- مرورگر: build واقعی + preview روی 0.0.0.0 و Playwright/Chromium headless با دادهٔ ساختگی.
  اگر کتابخانهٔ سیستمی کم بود (libnspr4 و مانند آن)، نسخهٔ OSS جایگزین را امتحان کن؛ نشد → BLOCKED با خطای دقیق، نه PASS.
- بعد از push: gh pr checks و gh run list برای همان SHA؛ نتیجه را در evidence ثبت کن.
  CI سبز روی SHA دیگر یا worktree dirty شاهد این کار نیست.

۹) تعریف انجام‌شده (DoD)
PASS فقط وقتی: AC همان کارت رعایت شده + تست/گیت روی همین SHA اجرا شده + خروجی ثبت شده +
بدون regression (lint/build/test همان حوزه و همسایه‌ها) + مجوز سمت سرور آزموده شده (هرجا نقش دخیل است) +
سند/handoff به‌روز.
PASS نیست: mock یا fallback، screenshot تنها، تست skip‌شده، CI روی commit دیگر، «صفحه هست»، «API هست» بدون نقش/مالکیت،
و هر ادعایی که خودت اجرا نکرده‌ای. وضعیت میانی را PARTIAL بگذار با دلیل باقی‌ماندهٔ دقیق.
DONE یعنی شاهد در یک commit روی ریموت (push‌شده) وجود دارد؛ «فایل در worktree محلی» DONE نیست.
اگر evidence/… یا STATE فقط local ماند، همان item PARTIAL است — نه DONE و نه PASS.
subagent یا review مستقل را ادعا نکن؛ اگر خودت اجرا نکردی بنویس «مرور دستیِ ایجنت اصلی».

۱۰) قالب ثبت شاهد (برای هر item)
  ID و parent PWA-*:
  وضعیت: PROPOSED | READY | IN_PROGRESS | PARTIAL | PASS | BLOCKED | UNKNOWN | NOT_RUN
  دلیل تغییر وضعیت:
  SHA / diff fingerprint / محیط:
  وابستگی‌ها و تصمیم مصوب:
  فایل/route/API/نقش‌های تحت پوشش:
  دستورها + نسخهٔ ابزار + cwd:
  نتیجه pass/fail/skip (+ تست منفی):
  لینک شاهد پالایش‌شده:
  ریسک باقی‌مانده / blocker / جبران:
  وضعیت برگشت‌پذیری:

۱۱) STATE و ادامهٔ خودکار
فایل docs/MuscleParadise/PWA-EXECUTION-STATE.md را با این جدول بساز و هر چرخه به‌روز کن:
ترتیب | ID | parent | وضعیت | شاهد | اقدام بعدی دقیق | blocked_by | دستور ادامه
- بالاترین ردیف باز همیشه «اقدام بعدی» است.
- پایین فایل همیشه یک «کارت ادامه» داشته باشد: SHA، شاخه، فرمان بعدی، و آخرین چیز سبز.
- STATE/HANDOFF را با transcript پر نکن؛ فقط چیزی که نشست بعد لازم دارد.

۱۲) قواعد ضد اتلاف
- هر چرخه باید یک diff واقعی (کد/تست) یا یک blocker ثبت‌شده تولید کند؛ «سند برنامه‌ریزی جدید» جای کار نیست.
- از خواندن کل فایل‌های بزرگ، تست کامل بی‌دلیل، و تکرار گیت‌های سبزشده پرهیز کن؛ checkpoint هر ۵ item یا قبل از push.
- گزارش چرخه کوتاه و ساختاری (بند ۱۴)؛ توضیح بلند فقط وقتی خواسته شد.
- سه تلاش پیاپی ناموفق روی یک مشکل ⇒ همان item را BLOCKED کن با خطای دقیق و برو سراغ بعدی.
- وابستگی/فایل تازه فقط با توجیه در evidence (نسخه، license، جایگزین موجود).

۱۳) حفاظت شواهد
- خروجی خام گیت‌ها را در evidence/<تاریخ>/<ID>/ نگه دار؛ متن‌ها پالایش‌شده و بدون secret/PII.
- فایل‌های خصوصی/رسید/دادهٔ واقعی نه در docs باز می‌شوند نه commit.
- مسیر استاندارد شاهد: evidence/<تاریخ>/<ID>/ (همان تاریخ tracker، مثلاً evidence/2026-11-23/INV-02/).
- بعد از هر push، وجود شاهد روی ریموت را چک کن (git ls-remote یا API contents) و در STATE بنویس.
- هر عدد در گزارش باید از خروجی همان اجرا آمده باشد؛ اگر شک داری، «اجرا نشد» بنویس.

۱۴) گزارش پایان چرخه و شرایط توقف
گزارش:
  DONE: <IDها> | وضعیت: از X به Y | شاهد: <دستور + نتیجهٔ عددی>
  DIFF: <فایل‌های اصلی>
  گیت‌ها: lint/build/test/docs → pass/fail
  NEXT: <ID بعدی> — <یک جمله چرا>
  BLOCKED: <IDs + دلیل یک‌خطی>  (در صورت وجود)

توقف فقط در این حالت‌ها:
(الف) همهٔ itemهای بخش ۳ بسته یا BLOCKED/UNKNOWN با شاهد شده‌اند و کار مستقل نمانده →
      گزارش «پایان صف محلی» + فهرست بلاکرها + پرسش‌های مالک (هر کدام یک خط با گزینه‌ها).
(ب) مالک صریحاً «توقف» بدهد.
(ج) کار بعدی فقط با تصمیم برگشت‌ناپذیر/خارج از scope بند ۵ جلو می‌رود.
(د) محدودیت سخت محیط بدون ابزار جایگزین — که فقط همان item را متوقف می‌کند، نه حلقه را.
در حالت (الف) و (د) قبل از پایان، STATE را طوری بنویس که «ادامه» دقیقاً از کار درست شروع شود.

شروع: همین حالا بند ۱ و ۲ را انجام بده، STATE را بساز یا بخوان، اولین item را انتخاب کن و
بدون پرسیدن سؤال، چرخه را تا شرایط توقف بند ۱۴ ادامه بده.

۱) SHA امن‌شده بگیر، نه شاخهٔ محلی خودت

  cd <repo MP>
  git fetch origin
  git status --short --branch        # کار dirty خودت را حفظ کن، پاک نکن
  TARGET=$(git rev-parse origin/main)
  echo "TARGET=$TARGET"

اگر شاخهٔ کاری‌ات dirty است، در worktree جدا اجرا کن تا خروجی به SHA تمیز بچسبد:

  cd /tmp/inv-redo
