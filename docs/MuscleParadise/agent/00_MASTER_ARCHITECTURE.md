# ۱. هدف برنامه — در یک پاراگراف

**Muscle Paradise یک سیستم‌عامل باشگاه بدن‌سازی است که کاملاً محلی کار می‌کند.**
یک مربی شخصی که آنالیز ترکیب بدنی Jackson–Pollock 7 انجام می‌دهد، با آن اعضا را مدیریت
می‌کند، برنامهٔ تمرینی **آگاه به مصدومیت** می‌سازد، حضور و غیاب و مالی را می‌گرداند —
بدون هیچ سرور ابری، بدون هزینهٔ ماهانه، و بدون اینکه دادهٔ سلامتی ورزشکار از LAN باشگاه
خارج شود. رابط کاربری فارسی-اول با تقویم جلالی و واحد ریال است.

## ۱.۱ چهار نسخهٔ محصول (تصمیم قطعی)

```
                  یک کدپایهٔ React  (نصفش از قبل موجود است)
                  ├── admin  entry ──┬── Tauri Desktop → 1. ادمین دسکتاپ
                  │  (index.html)    └── Tauri Android → 2. ادمین موبایل
                  └── client entry ──┬── Tauri Desktop → 3. کلاینت دسکتاپ
                     (client.html)   └── Tauri Android → 4. کلاینت موبایل
                                              ↕ LAN (HTTP)
                        یک FastAPI روی PC باشگاه (موجود، ۲۷۶ تست سبز)
```

| تصمیم | حکم | دلیل |
|---|---|---|
| پوسته: **Tauri v2** به‌جای Electron | ✅ | نصب‌کننده از ۸۴MB → ~۱۰MB · RAM نصف · موبایل دارد |
| بک‌اند: **Python بماند** | ✅ | ۲۷۶ تست و ریاضی قفل‌شده؛ بازنویسی Rust = ۴ ماه، صفر سود کاربری |
| موبایل: **فقط اندروید** | ✅ | بدون مک، بدون Xcode، بدون حساب اپل |
| ورود کیوسک | ✅ | **QR و تشخیص چهره، هر دو در v1** (بخش ۶) |
| ویدیوی آموزشی | ✅ | به‌صورت Knowledge Pack دانلودی، نه داخل نصب‌کننده |

## ۱.۲ مرز دسترسی — ادمین در برابر کلاینت

**قانون بنیادین: مرز امنیتی سرور است، نه اپ.**
حتی اگر چهار باینری جدا بسازیم، اگر سرور اجازه بدهد، کسی با `curl` همه‌چیز را می‌خواند.

# ۵. پروتکل کیفیت — دروازه‌های غیرقابل‌مذاکره

هیچ تسکی `DONE` نمی‌شود مگر **هر پنج** دروازه سبز باشد:

```bash
# G1 — بک‌اند
cd mp-app/backend && pytest --override-ini="addopts=" -q --cov=app --cov-fail-under=85

# G2 — فرانت
cd mp-app/studio && npm run gate

# G3 — امنیت
bandit -q -c mp-app/backend/bandit.yaml -r mp-app/backend/app -ll
pip-audit -r mp-app/backend/requirements.txt --strict

# G4 — همگامی اسپک
cd mp-app/backend && python -m app.export_openapi --yaml > /tmp/o.yaml && diff ../openapi.yaml /tmp/o.yaml

# G5 — معماری
grep -rl "^from fastapi\|^import fastapi" mp-app/backend/app/core/ && exit 1 || true
```

**قانون طلایی:** اگر عددی را نمی‌توانید اندازه بگیرید، آن کار تمام نشده است.

# ۶. تشخیص چهره — قابلیت v1 (ثبت رسمی)

**خواسته:** تبلت دم در ورودی؛ ورزشکار در لحظهٔ ورود با چهره ثبت شود.
**حکم: در v1 ساخته می‌شود.** بازار هدف ایران است و محدودیت مقرراتی GDPR اعمال نمی‌شود.

> **آنچه حذف *نمی‌شود*:** الزامات **مهندسی**. تشخیص چهره بدون تشخیص زنده‌بودن،

## ۶.۱ چرا liveness غیرقابل‌مذاکره است

بدون آن، این حمله در ۱۰ ثانیه کار می‌کند:
```
مهاجم عکس عضو را از اینستاگرام برمی‌دارد → روی گوشی نمایش می‌دهد
→ جلوی تبلت می‌گیرد → در باز می‌شود
```
برای سیستمی که پول عضویت به آن وصل است، این نقص کشنده است.
**دفاع سه‌لایه** (هر سه در `LOOP_F`):
| لایه | روش |
|---|---|
| ۱ | **ضدجعل غیرفعال** — تشخیص بافت پوست، بازتاب، مویر صفحهٔ نمایش |
| ۲ | **بررسی عمق** — اگر تبلت دو دوربین دارد؛ وگرنه اختلاف منظر حرکتی |
| ۳ | **چالش فعال** (در صورت شک) — «سرت را کمی بچرخان» / پلک بزن |

## ۶.۲ معیار پذیرش عددی (C12)

| سنجه | هدف | معنی |
|---|---|---|
| FAR (پذیرش اشتباه) | **< ۰.۰۱٪** | یک نفر از ۱۰٬۰۰۰ به‌جای دیگری وارد شود |
| FRR (رد اشتباه) | **< ۳٪** | عضو واقعی گاهی رد شود (بعد قابل QR) |
| نرخ شکست ضدجعل | **< ۱٪** روی مجموعهٔ حملهٔ عکس/ویدیو/ماسک | |
| زمان اسکن تا در | **< ۱ ثانیه** | |
| ظرفیت | **۲۰۰۰ قالب** روی CPU تبلت | |

اینها با **مجموعهٔ آزمون واقعی** سنجیده می‌شوند، نه با حس خوب.

## ۶.۳ معماری — همه‌چیز محلی

```
دوربین تبلت → تشخیص چهره (ONNX محلی) → بررسی liveness
            → استخراج بردار ۵۱۲ بُعدی → جست‌وجوی نزدیک‌ترین همسایه
            → آستانهٔ شباهت → ثبت حضور
```
| تصمیم | مقدار |
|---|---|
| مدل | ONNX محلی (InsightFace/ArcFace) — **هیچ سرویس ابری** |
| اجرا | روی تبلت یا PC باشگاه؛ کاملاً آفلاین (C1) |
| ذخیره | فقط **بردار ریاضی**؛ عکس خام بعد از ثبت‌نام حذف |
| رمزنگاری | قالب‌ها با کلید محلی رمز شوند |

## ۶.۴ الزاماتی که به دلایل *مهندسی* می‌مانند

| # | الزام | چرا (نه حقوقی — عملی) |
|---|---|---|
| ۱ | **QR همیشه به‌عنوان جایگزین فعال بماند** | FRR هرگز صفر نیست. عضو با آرایش تازه، عینک، یا نور بد باید بتواند وارد شود. بدون این، صف جلوی در |
| ۲ | ثبت‌نام صریح توسط عضو | ثبت‌نام مخفی = بی‌اعتمادی و ریزش عضو |
| ۳ | دکمهٔ «چهره‌ام را حذف کن» | عضو مالک دادهٔ خودش است؛ اعتماد سرمایهٔ باشگاه است |
| ۴ | قالب‌ها رمزشده روی دیسک | سرقت PC باشگاه نباید بیومتریک ۲۰۰۰ نفر را لو دهد |
| ۵ | ثبت هر تطبیق در `audit_log` | برای عیب‌یابی «چرا در باز نشد» و اثبات حضور |

## ۶.۵ برنامهٔ ساخت
`LOOP_F` (۲۴ تسک) کامل می‌سازد: QR (پایهٔ مطمئن) **و** خط لولهٔ تشخیص چهره با liveness.
QR اول ساخته می‌شود چون تکیه‌گاه است، نه چون چهره موکول شده.
