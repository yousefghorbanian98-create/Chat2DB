# LOOP D — پوستهٔ Tauri (چهار نسخه)
## ۳۰ تسک · ~۴ هفته · وابسته به LOOP A

**هدف:** از Electron ۸۴MB به چهار باینری Tauri (~۱۰MB هرکدام) از **یک** کدپایه.

---

## ⚠️ دو واقعیت که باید قبل از شروع بدانید

**۱. پلاگین‌های `barcode-scanner` و `biometric` فقط Android/iOS هستند — روی دسکتاپ وجود ندارند.**
کیوسک شما دسکتاپ است. پس اسکن QR روی دسکتاپ باید با `getUserMedia` در خود WebView
انجام شود، یا با **اسکنر سخت‌افزاری USB** (که برای کیوسک واقعی بهتر و سریع‌تر است).

**۲. ساخت Rust کندتر از باندل JS است.** انتظار CI را تنظیم کنید (~۴ دقیقه به‌جای ~۲).

# فاز D1 — پیکربندی چهار هدف (تسک ۰۴–۰۹)

## D-04 · چهار پیکربندی Tauri
```
shell/tauri.admin.desktop.conf.json    → index.html  + sidecar هسته
shell/tauri.admin.android.conf.json    → index.html  (کلاینت نازک)
shell/tauri.client.desktop.conf.json   → client.html
shell/tauri.client.android.conf.json   → client.html
```
شناسه‌های جدا: `app.muscleparadise.admin` / `.client`

## D-05 · قابلیت‌های حداقلی (least privilege)
`shell/capabilities/` — **مهم‌ترین مزیت امنیتی Tauri v2**.
- ادمین دسکتاپ: fs (محدود به پوشهٔ داده) · shell (فقط sidecar) · updater
- کلاینت: **بدون fs** · بدون shell · فقط http به LAN + barcode-scanner (اندروید)

⚠️ اپ کلاینت نباید هیچ دسترسی فایل‌سیستمی داشته باشد. اگر دارد، اشتباه است.

## D-06 · هسته به‌عنوان sidecar (فقط ادمین دسکتاپ)
Python + هسته را با PyInstaller بسته‌بندی و به‌عنوان sidecar اجرا کنید.
مدیریت چرخهٔ عمر: بالا آمدن، سلامت، **توقف مؤدبانه** (checkpoint شدن WAL).

## D-07 · کشف سرور روی LAN (سه اپ دیگر)
اولین اجرا: ورود دستی آدرس **یا** کشف mDNS.
⚠️ **اعتبارسنجی ورودی:** فقط `http(s)` + host. (همان اشتباهی که در وب‌هوک بود.)

## D-08 · CSP سخت در Tauri
`connect-src` فقط به هستهٔ پیکربندی‌شده.

## D-09 · به‌روزرسان امضاشده — پایه
`tauri-plugin-updater` با کلید عمومی. **بدون تأیید امضا فعال نشود** (B-21).
این تسک فقط مسیر پایه را باز می‌کند؛ **به‌روزرسانی تفاضلی در فاز D4** ساخته می‌شود.

# فاز D4 — به‌روزرسانی تفاضلی (تسک ۲۳–۳۰) 📦

> **مسئله.** نصب‌کنندهٔ ادمین دسکتاپ با sidecar پایتون حدود **۶۰–۹۰ MB** است.
> اگر برای اصلاح یک متن یا یک باگ کوچک، کاربر مجبور باشد کل آن را دوباره
> دانلود کند، در ایران با اینترنت گران و بی‌ثبات، **به‌روزرسانی نمی‌کند** —
> و شما به باشگاه‌هایی خدمات می‌دهید که هرکدام روی نسخهٔ متفاوتی مانده‌اند.
> این بدترین حالت ممکن برای پشتیبانی است.
>
> **هدف عددی این فاز: یک وصلهٔ معمولی < ۵ MB و نصب < ۳۰ ثانیه.**
>
> ⚠️ **قاعدهٔ طلایی به‌روزرسان:** به‌روزرسان تنها بخشی از برنامه است که اگر
> خراب شود، **نمی‌توانید با به‌روزرسانی درستش کنید**. این فاز را با وسواس
> بسازید و تست بازگشت (rollback) را جدی بگیرید.

## D-23 · لایه‌بندی مصنوع ساخت
پیش‌نیاز همه‌چیز: خروجی را به لایه‌هایی با نرخ تغییر متفاوت بشکنید.

| لایه | حجم تقریبی | هر چند وقت تغییر می‌کند |
|---|---|---|
| رانتایم پایتون + وابستگی‌ها | ~۴۵ MB | ماهی یک‌بار |
| کد هستهٔ `app/` | ~۲ MB | هر انتشار |
| دارایی‌های وب (JS/CSS) | ~۱ MB | هر انتشار |
| باینری Tauri | ~۶ MB | گاهی |
| بستهٔ دانش (ویدیو/مدل) | جدا | مستقل — از قبل جداست |

**verify:** `ls dist/layers/` چهار لایه را نشان دهد + `layers.json` با هش هر لایه

## D-24 · مانیفست نسخه با هش per فایل
`update-manifest.json`: نسخه، تاریخ، و برای هر فایل `{path, sha256, size}`.
همین مانیفست است که به سرویس‌گیرنده می‌گوید **چه چیزی واقعاً عوض شده**.
مانیفست **امضا** می‌شود (همان کلید D-09).

**verify:** `python scripts/verify_manifest.py dist/update-manifest.json` → exit 0

## D-25 · تولید وصلهٔ دودویی تفاضلی
با **`zstd --patch-from`** (BSD/GPL دوگانه — از باینری جدا استفاده کنید، لینک نکنید)
یا `bsdiff`. برای هر جفت نسخهٔ متوالی یک `.patch` بسازید:
`v1.2.0 → v1.2.1`. سرور آخرین **سه** نسخه را نگه می‌دارد؛ قدیمی‌تر از آن،
دانلود کامل.

**verify:** `scripts/make_patch.sh v1.2.0 v1.2.1` → فایل وصله < ۵ MB برای تغییر معمولی

## D-26 · منطق انتخاب سمت سرویس‌گیرنده
سرویس‌گیرنده مانیفست را می‌گیرد و تصمیم می‌گیرد:
۱. نسخه یکی است → کاری نکن.
۲. وصلهٔ مستقیم موجود است → وصله را بگیر.
۳. چند نسخه عقب است → وصله‌ها را زنجیره‌ای بگیر، **اگر** جمعشان < ۶۰٪ دانلود کامل بود.
۴. وگرنه → دانلود کامل.
تصمیم و دلیلش لاگ شود.

**verify:** `pytest tests/test_updater_decision.py` → هر چهار شاخه پوشش داده شود

## D-27 · اعمال اتمی + بازگشت
**این حساس‌ترین تسک فاز است.**
- وصله در پوشهٔ `staging/` اعمال شود، نه روی نصب زنده.
- بعد از اعمال، **هش هر فایل با مانیفست مقایسه شود**. یک عدم‌تطابق = لغو کامل.
- سپس جابه‌جایی اتمی پوشه‌ها و نگه‌داشتن نسخهٔ قبلی به‌عنوان `previous/`.
- اگر برنامه بعد از به‌روزرسانی **دو بار پشت‌سرهم** موقع بالا آمدن کرش کرد → خودکار به `previous/` برگرد و به کاربر اطلاع بده.
- قطع برق وسط کار نباید نصب را خراب کند.

**verify:** `pytest tests/test_updater_atomic.py` شامل تست قطع شبیه‌سازی‌شده

## D-28 · به‌روزرسانی مستقل بستهٔ دانش
ویدیوها و مدل ONNX چهره **نباید** با نسخهٔ برنامه گره بخورند.
مانیفست جدا، **دانلود per-فایل** (فقط ویدیوهای جدید/عوض‌شده)، قابل ازسرگیری
با `Range` header، و قابل توقف/ادامه. اضافه کردن ۱۰ ویدیوی جدید = دانلود ۱۰ ویدیو،
نه کل بسته.

**verify:** حذف ۳ ویدیو و اجرای همگام‌سازی → دقیقاً ۳ فایل دانلود شود

## D-29 · به‌روزرسانی اندروید
Google Play اینجا نیست (توزیع مستقیم APK). پس:
- **بررسی نسخه در اپ** + دانلود APK + نصب با `REQUEST_INSTALL_PACKAGES`.
- امضای APK جدید باید **با همان کلید** باشد وگرنه اندروید نصب را رد می‌کند — این را در CI قفل کنید.
- دارایی‌های وب داخل APK از طریق همان مانیفست D-24 به‌روز شوند، **بدون** نصب مجدد APK. اکثر تغییرات UI اینطور می‌رسند.

**verify:** به‌روزرسانی دارایی‌های وب بدون نصب مجدد APK کار کند

## D-30 · رابط کاربری و کنترل به‌روزرسانی
- تنظیمات: خودکار / فقط اطلاع بده / دستی. **پیش‌فرض: فقط اطلاع بده** (باشگاه وسط ساعت شلوغی نباید ری‌استارت شود).
- نمایش: نسخهٔ فعلی، نسخهٔ موجود، **حجم دقیق دانلود**، و تغییرات (changelog فارسی).
- «الان نه» باید واقعاً یعنی الان نه.
- دکمهٔ «بازگشت به نسخهٔ قبلی» برای صاحب باشگاه.

**verify:** `npm test -- UpdatePanel` → exit 0
