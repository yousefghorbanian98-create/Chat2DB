# 04 — فرانت‌اند

> منبع: `mp-app/studio/`. React 18 + TypeScript + Vite 6 + Framer Motion + Recharts.
> اعداد این سند خروجی واقعی `npm run gate` در همین بازبینی است.

---

## 1. معماری فعلی — دو پوستهٔ یک کدپایه

```
studio/
├── index.html      → main.tsx        → App.tsx        (Studio / مربی)
├── client.html     → client-main.tsx → ClientApp.tsx  (Client / ورزشکار)
└── electron/main.cjs                                  (پوستهٔ ویندوز)
```

یک مخزن، دو نقطهٔ ورود، دو خروجی Vite. **این انتخاب درستی است**: منطق مشترک
(`api/`, `core/jalali.ts`, `core/jp7.ts`, `motion/`) یک بار نوشته می‌شود و هر دو پوسته
از آن استفاده می‌کنند، ولی باندل هرکدام فقط کد خودش را دارد.

### لایه‌بندی
| پوشه | مسئولیت | قانون |
|------|----------|-------|
| `api/` | `client.ts` + `types.ts` | تنها جایی که `fetch` صدا زده می‌شود |
| `core/` | ریاضی خالص (jp7، jalali) | بدون React، بدون I/O، ۱۰۰٪ تست‌پذیر |
| `hooks/` | حالت + هماهنگی | هر hook یک قابلیت |
| `components/` | نمایشی | بدون فراخوانی مستقیم API |
| `pages/` | ترکیب | با `lazy()` بارگذاری می‌شوند |
| `motion/presets.ts` | واژگان حرکت | هیچ‌جا عدد جادویی انیمیشن نباشد |
| `styles/tokens.css` | توکن‌های طراحی | هیچ رنگ هارد-کد در کامپوننت |

قانون «تنها `api/client.ts` حق `fetch` دارد» را با یک قاعدهٔ ESLint سخت کنید
(`no-restricted-globals: fetch` با استثنا برای همان فایل). الان قانون نانوشته است.

### 🔴 مشکل شمارهٔ یک فرانت: چانک ۱۱۱ kB برای JP7
صفحهٔ سنجش تقریباً **به‌اندازهٔ کل بقیهٔ برنامه** وزن دارد. علتش Recharts است.
این صفحه‌ای است که مربی روزی ده بار باز می‌کند.

**سه راه‌حل، به ترتیب ارجحیت:**
1. **نمودار را از فرم جدا کنید.** فرم ورود ۷ پوست‌چین فوراً بیاید؛ نمودار تاریخچه
   با `lazy()` جداگانه و پس از تعامل بارگذاری شود. → ورود صفحه به ~۱۵ kB می‌رسد.
2. **Recharts را با یک SVG دست‌ساز عوض کنید.** نمودار خط تک‌متغیرهٔ درصد چربی،
   ۸۰ خط SVG است، نه ۱۰۰ kB کتابخانه.
3. اگر Recharts می‌ماند، فقط ماژول‌های لازم را import کنید و `manualChunks` بسازید.

### 🔴 مشکل دوم: vendor 108 kB بدون نام معنادار
چانک `tokens-BR8iTfOk.js` در واقع vendor است (React + Framer Motion). نامش گمراه‌کننده است و
هیچ `manualChunks` صریحی تعریف نشده. تعریف کنید:
```ts
// vite.config.ts
build: { rollupOptions: { output: { manualChunks: {
  react: ['react', 'react-dom'],
  motion: ['framer-motion'],
}}}}
```
تا به‌روزرسانی یک صفحه، کش React کاربر را باطل نکند.

## 4. مدیریت حالت و داده

اکنون: hookهای دست‌ساز با `useState`/`useEffect`.
برای اندازهٔ فعلی قابل قبول است، ولی سه چیز غایب است که به‌زودی درد می‌شود:

| نیاز | راه‌حل پیشنهادی |
|------|------------------|
| کش، حذف تکرار درخواست، revalidate | **TanStack Query** — هستهٔ آن ~۱۳ kB gzip |
| به‌روزرسانی خوش‌بینانه در شبکهٔ ضعیف | همان (`onMutate` + rollback) |
| صف آفلاین برای ثبت ست تمرین | صف در IndexedDB + پخش هنگام آنلاین شدن |

آخری برای «local-first» بودن **اساسی** است: ورزشکار در زیرزمین باشگاه بدون Wi-Fi
باید بتواند ست ثبت کند و بعداً همگام شود. اکنون `workoutDraft.ts` فقط پیش‌نویس داخل حافظه
نگه می‌دارد؛ رفرش صفحه = از دست رفتن داده.

## 5. RTL و فارسی — چه چیزی درست است، چه چیزی نه

### ✅ درست
- تبدیل جلالی با ۹ لنگر آزموده (نوروز ۱۴۰۵، اسفند کبیسه) در برابر `jdatetime`.
- `prefers-reduced-motion` در سه فایل تست پوشش داده شده.
- فونت فارسی محلی (`assets/fonts/PersianSans-Regular.ttf`) — بدون Google Fonts، مطابق local-first.

### 🔴 نیازمند کار
1. **رشته‌ها هارد-کد فارسی هستند.** انگلیسی (زبان دوم مصرح در نقشه) غیرممکن است.
   راه‌حل سبک: یک `t()` ساده با فایل JSON، نه i18next سنگین.
   ```ts
   // i18n/fa.json — { "auth.invalid": "نام کاربری یا رمز اشتباه است" }
   ```
2. **منطقی-محور بنویسید، نه جهت‌محور.** به‌جای `margin-left` از `margin-inline-start`
   استفاده کنید، وگرنه سوئیچ به LTR کل چیدمان را می‌شکند. یک قاعدهٔ stylelint این را می‌گیرد.
3. **ارقام فارسی فقط در نمایش.** ذخیره و ورودی باید لاتین بماند. یک تابع `toFaDigits()`
   در لایهٔ نمایش، و **هرگز** در لایهٔ داده.

## 6. دسترس‌پذیری — وضعیت و برنامه

اکنون تست a11y سیستماتیک وجود ندارد (فقط `motionA11y.test.tsx`).

**سه اقدام مشخص:**
```bash
npm i -D vitest-axe @axe-core/cli
```
1. در هر تست صفحه: `expect(await axe(container)).toHaveNoViolations()`.
2. کنتراست توکن‌های `tokens.css` را یک بار با ابزار بسنجید و نتیجه را در سند ۰۹ ثبت کنید.
3. کیوسک: هدف لمسی ≥ ۴۴px، فوکوس قابل‌رؤیت، و **خروج فقط با PIN** (پیاده شده).

## 7. PWA و آفلاین

`public/sw.js` (۱۰۳ خط) دست‌نویس است. برای این حجم قابل قبول است، ولی:
- **استراتژی کش را مستند کنید:** پوسته = cache-first، API = network-first با fallback.
- **نسخه‌بندی کش** بگذارید (`mp-v0.20.0`) و در `activate` کش‌های قدیمی را پاک کنید،
  وگرنه کاربران بعد از به‌روزرسانی، نسخهٔ کهنه می‌بینند — کلاسیک‌ترین باگ PWA.
- یک تست دارد (`pwa.test.tsx`) ✅ — آن را گسترش دهید تا پاکسازی کش را هم بسنجد.

## 8. حرکت (Motion) — تعارض حل‌شده

سند طراحی، تعارض واقعی را درست حل کرده و باید حفظ شود:

| سطح | دیال حرکت | قاعده |
|-----|-----------|-------|
| صفحهٔ فرود، مودال، توست، جشن | **8/10** سینمایی | spring، `back.out` مجاز |

همهٔ مقادیر باید از `motion/presets.ts` بیایند — عدد جادویی داخل کامپوننت ممنوع.

## 9. اپ اندروید — وضعیت واقعی

`android/.../MainActivity.java` یک **پوستهٔ WebView** است که در اولین اجرا آدرس سرور را می‌گیرد.

این را با صداقت به کاربر بگویید (که در `PROJECT_SUMMARY_FA.md` گفته شده ✅). اما دو ریسک امنیتی:
1. **`cleartextTraffic` مجاز است.** روی Wi-Fi عمومی باشگاه، توکن ورزشکار متن ساده رد می‌شود.
   حداقل: TLS خودامضا با pinning، یا محدود کردن cleartext به بازه‌های خصوصی
   (`network_security_config.xml` با `<domain>192.168.0.0/16</domain>`).
2. **بدون اعتبارسنجی ورودی آدرس سرور.** کاربر می‌تواند هر URL بدهد؛ WebView هرچه بیاید اجرا می‌کند.

**مسیر درست برای v1.0:** یا Flutter بومی (طبق نقشه)، یا حداقل یک WebView سخت‌شده با
`network_security_config` و فهرست سفید میزبان.
