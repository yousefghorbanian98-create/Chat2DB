② یک تصحیح حسابی — بار سوم
────────────────────────────────────────────
گفتی `BRANCH_VS_MAIN: ahead=20`. من از API گرفتم:

      compare(main...74033cb): ahead=19 behind=0 files=49 commits=19

هر دور یک عدد بیشتر می‌گویی (۱۷→۱۸→۲۰ در برابر واقعی ۱۷→۱۸→۱۹). احتمالاً
`git rev-list --count` را محلی و روی شاخهٔ محلی می‌گیری که یک کامیت از ریموت
عقب‌تر است. کار:

      git fetch origin
      gh api repos/<R>/compare/main...$(git rev-parse HEAD) -q '.ahead_by'

و همان عدد API را بنویس، نه `rev-list` محلی. شاهد لازم نیست — فقط عدد درست.

────────────────────────────────────────────
③ MEM-10 — یک شکاف جدی پیش از UI
────────────────────────────────────────────
مسیر را درست پیدا کردی: `GET /face_id/qr-token` + `POST /face_id/checkin-qr`
با `exp` دو دقیقه‌ای و `qr_replayed` (۴۰۹). ولی قبل از ساختن UI، این را جواب بده:

      آیا `POST /face_id/checkin-qr` واقعاً **جایگزین** است یا روی
      یک ردیف جدید می‌نشیند؟ و ایندکس یکتا روی کدام ستون‌هاست؟

و مهم‌تر — سه حالتی که در TODO آمده و باید **در backend** آزموده شوند، نه در UI:

  1. **replay:** همان توکن دو بار → بار دوم `409 qr_replayed`
  2. **انقضا:** توکنی با `exp` گذشته → `401/403`، نه ۲۰۰
  3. **عضو دیگر:** توکن صادرشده برای A، با توکن دسترسی B → `403`

اگر هر سه در `tests/integration/` پوشش دارند، فقط شاهد را بخوان و ثبت کن.
اگر ندارند، **اول تست بنویس**، بعد UI. UI که روی قرارداد آزموده‌نشده ساخته شود،
همان چیزی است که «دکمهٔ disabled» را به «اثبات حضور» تبدیل می‌کند.

و یک هشدار که در TODO هم آمده: **`QR محلی به‌تنهایی حضور/هویت اثبات نمی‌کند`.**
پس UI باید این را صریح بگوید، نه اینکه «حضور ثبت شد ✅» نشان دهد.
متن پیشنهادی: «حضور شما برای این نشست ثبت شد؛ تأیید نهایی توسط مربی/سیستم.»

**face recognition اضافه نکن.** اسم ماژول `face_id` است، ولی در scope نیست.
