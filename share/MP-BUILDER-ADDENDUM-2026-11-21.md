## بخش ۳ · WP ‏2.6 (جدید، فاز ۲) — F‑29: لاگِ بدون traceback در مسیر SMS

**شدت:** Low‑Medium. **ریشه:** `app/sms.py`.

**۳‑۱) شش `logging.error` داخل `except`** — قاعدهٔ `TRY400`:

```
app/sms.py:66:13   app/sms.py:69:13   app/sms.py:72:13
app/sms.py:99:13   app/sms.py:102:13  app/sms.py:105:13
   → TRY400 Use `logging.exception` instead of `logging.error`
```

`logging.error()` داخل بلاک `except` **فقط پیام** را ثبت می‌کند و زنجیرهٔ فراخوانی را
دور می‌ریزد؛ `logging.exception()` همان پیام را **با traceback** می‌نویسد.
نتیجهٔ عملیِ امروز: هر بار فراهم‌کنندهٔ SMS خطا بدهد، در لاگ «ارسال ناموفق» دیده می‌شود
ولی **نه** کد خطای HTTP، **نه** timeout، **نه** DNS، **نه** بدنهٔ پاسخ —
دقیقاً همان چیزی که برای تفکیکِ «باگِ ما» از «قطعیِ فراهم‌کننده» لازم است.

**چرا این در فاز ۲ (قابلیت اتکا) است:** SMS پرخطاترین مسیرِ **خروجیِ شبکه** است و
کم‌لاگ‌ترین. این مورد با **F‑03** (WP ‏2.1) ترکیب می‌شود: اگر F‑03 را رفع کنی ولی
F‑29 را نه، لاگ‌ها تمیز می‌شوند ولی **بی‌محتوا**. پس این دو WP را پشتِ سر هم انجام بده.

**۳‑۲) سه `urlopen` با schemes باز** — قاعدهٔ `S310`:

```
app/sms.py:52   app/sms.py:61   app/sms.py:94
```
`urllib.request.urlopen` به‌طور پیش‌فرض `file://` و `ftp://` را هم می‌پذیرد.
اگر host از یک setting بیاید (`sms_provider_url`)، مقدارِ دست‌کاری‌شده می‌تواند به
خواندنِ فایلِ محلی بینجامد. **شدتِ عملی کم است** چون مقدار از محیط خوانده می‌شود
نه از ورودی کاربر — ولی یک allowlist از schemes هزینهٔ صفر دارد:

```python
from urllib.parse import urlparse
_ALLOWED = {"http", "https"}
if urlparse(url).scheme not in _ALLOWED:
    raise ValueError(f"scheme نامعتبر برای ارائه‌دهندهٔ پیامک: {url!r}")   # یا # noqa: S310 مستند
```

(سه موردِ دیگرِ `S310` در `eval/llm_column.py:59,100,107` است — آن‌ها در
`per-file-ignores` پوشش داده شده‌اند چون `eval/` ابزارِ توسعه است، نه مسیرِ محصول.)

**۳‑۳) پاک‌سازی ۳۹ `# noqa` بلااثر** — قاعدهٔ `RUF100` (بخشی از همان ۴۷ رفعِ خودکارِ WP ‏0.9).
چهار موردش روی همان خطوطِ F‑22 است (بخش ۵ را بخوان).

**۳‑۴) مواردِ هم‌خانواده که باید در همین WP تعیین تکلیف شوند**
(چون همان قاعده‌ها در جای دیگری از کد هم fire می‌شوند):

| قاعده | محل | چه کنی |
|---|---|---|
| `S110` (try‑except‑pass) | `api/v1/monitoring.py:24` | **در WP ‏2.5 (F‑17) رفع می‌شود** — فقط مطمئن شو رها نشده |

## بخش ۴ · WP ‏3.6 (جدید، فاز ۳) — F‑28: سه برداشتِ متفاوت از «امروز» در یک محصول

**شدت:** Medium. **قاعدهٔ کاشف:** `DTZ011` (از خانوادهٔ `flake8-datetimez` که امروز خاموش است).

| محل | کدِ امروز | چه چیزی را «امروز» می‌گیرد |
|---|---|---|
| `modules/axis_assessment/service.py:31` | `today = date.today()` | **سنِ عضو** در ارزیابی محور‌ها |
| `modules/nutrition/service.py:124` | `day = entry.get("logged_for_date") or date.today().isoformat()` | روزِ پیش‌فرضِ **ثبت غذایی** |
| `modules/nutrition/service.py:182` | `day = day or date.today().isoformat()` | همان، شاخهٔ دوم |
| `modules/shop/service.py:61-62` | `ZoneInfo(settings.shop_timezone)` + `astimezone(zone)` | ✅ **درست — الگوی مرجع داخلِ همان پروژه** |
| `app/config.py:67,91-99` | `shop_timezone = "Asia/Tehran"` + اعتبارسنج با `ZoneInfo` | ✅ **درست — تنظیم و اعتبارسنجی موجود است** |

**چرا خطاست:** `date.today()` از ساعتِ **محلیِ فرایند** استفاده می‌کند و در کانتینر آن ساعت UTC است.
شاهد: `grep` روی `mp-app/infra/Dockerfile.backend`، `infra/docker-compose.yml`،
`backend/Dockerfile` و `infra/ansible/` ⇒ **۰ مورد تنظیمِ `TZ`**.

**اثباتِ مرز (این را خودت هم اجرا کن و در لاگ بگذار):**

```bash
python3 - <<'PY'
from zoneinfo import ZoneInfo
from datetime import datetime, UTC
now = datetime(2026, 11, 21, 22, 0, tzinfo=UTC)     # ۰۱:۳۰ بامدادِ ۲۲ آبان در تهران
print("UTC    :", now.date())
print("Tehran :", now.astimezone(ZoneInfo("Asia/Tehran")).date())
PY
# خروجیِ اندازه‌گیری‌شده:
#   UTC    : 2026-11-21     ← چیزی که date.today() در کانتینر می‌دهد ⇒ غلط
#   Tehran : 2026-11-22     ← آنچه کاربر و ماژول shop انتظار دارند
```

**بازهٔ خرابی:** هر شب از **۰۰:۰۰ تا ۰۳:۳۰ به وقت تهران** (۳٫۵ ساعت از هر ۲۴ ساعت = ۱۴٫۶٪ روز).

**تأثیر کاربری (نه فنی):**
- ثبتِ غذاییِ بدون `logged_for_date` روی **تاریخِ دیروز** می‌نشیند ⇒ تقویمِ کالری/وزن
  یک روز جابه‌جا می‌شود و هر نمودارِ «امروز» در UI اشتباه نشان می‌دهد.
- سنِ عضو در ارزیابیِ محور‌ها **دیرتر از موعد** یک سال بالا می‌رود ⇒ اگر تولدش همان روز باشد،
  تا سه‌ونیم ساعت بعد از نیمه‌شبِ تهران، ارزیابی با سنِ سالِ قبل انجام می‌شود
  (و `engine/axis_prescription.py` نسخهٔ متناسب با سنِ غلط می‌دهد).
- همزمان `shop` با منطقهٔ زمانیِ درست کار می‌کند ⇒ **سه برداشتِ متفاوت از «امروز»**
  در یک محصول (nutrition/axis با UTC، shop با تهران).

**اقدام (ترجیحاً هر دو، نه یکی):**

1. یک تابعِ مشترک بساز و هر سه محل را به آن ببر — **بدون تغییرِ API عمومی**:

```python
from datetime import UTC, date, datetime
from zoneinfo import ZoneInfo
from app.config import settings

def today_in_shop_zone() -> date:
    """«امروز» بر پایهٔ منطقهٔ زمانیِ پیکربندی‌شدهٔ محصول، نه ساعتِ کانتینر."""
    return datetime.now(UTC).astimezone(ZoneInfo(settings.shop_timezone)).date()
```

2. `ENV TZ=Asia/Tehran` را در `mp-app/infra/Dockerfile.backend` و `backend/Dockerfile`
   اضافه کن (و `tzdata` در image پایه موجود باشد). این **به‌تنهایی کافی نیست**
   چون به رفتارِ کانتینر وابسته است، ولی لایهٔ دومِ دفاع است و لاگ‌ها را هم هم‌تراز می‌کند.
3. یک تستِ مرزی بنویس که **ساعت را منجمد** کند (الگویش در WP‑های مربوط به QF‑10 بریف هست):
   با ساعتِ ۲۲:۰۰ UTC، روزِ ثبتِ غذایی باید `2026-11-22` باشد.
4. `grep -rn "date.today()\|datetime.now()" --include=*.py modules app engine jobs` را
   در CI به‌عنوان قاعدهٔ `DTZ011/DTZ001` گیت کن (امروز: ۳ موردِ `date.today()` +
   ۱ موردِ `DTZ001` در `tests/regression/test_manual_transfer_policy.py:165`).

**گیت عددیِ پذیرشِ WP ‏3.6:**

```bash
grep -rn "date.today()" modules app engine jobs     # ⇒ ۰ مورد (امروز ۳)
ruff check --no-cache --select DTZ .                # ⇒ ۰ مورد (امروز ۴: DTZ011×3 + DTZ001×1)
pytest tests/regression/test_*timezone* -q          # ⇒ تستِ مرزیِ نیمه‌شب پاس
```

## بخش ۵ · تصحیحِ WP ‏4.5 (بندِ F‑22) — این را **قبل از** دست‌زدن به آن بخوان

در پرامپتِ اصلی، WP ‏4.5 نوشت: «۴ مورد SQL با f‑string در
`db/migrations/versions/c3f01ab129e2_…py:67,165,169,171` را به
`op.execute(sa.text(...).bindparams(...))` یا `quoted_name` تبدیل کن» و
«Semgrep ⇒ ۰ یافته در هر سه قاعده».

**دو تصحیح:**

1. **ruff آن ۴ خط را نمی‌گیرد.** آزمونِ مستقیم:

```bash
ruff check --no-cache --select S608 --ignore-noqa .
# ⇒ All checks passed!     (صفر مورد)
```

یعنی `S608` روی `op.execute(f"DROP INDEX IF EXISTS ix_{table}_updated_at")` **fire نمی‌شود**،
چون ruff آن را SQLِ قابل‌تزریقِ «کامل» تشخیص نمی‌دهد (فقط `DROP INDEX` است،
نه `SELECT/INSERT` با شرط). **نتیجه: ruff جایگزینِ semgrep نیست.**
قاعدهٔ اختصاصیِ `harness/semgrep-mp.yml` را برای F‑22 **حذف نکن** و در CI نگه دار.

2. **آن `# noqa: S608`ها امروز هیچ اثری ندارند.** خودِ ruff می‌گوید چرا:

```
db/migrations/versions/c3f01ab129e2_…py:67:68:  RUF100 [*] Unused `noqa` directive (non-enabled: `S608`)
db/migrations/versions/c3f01ab129e2_…py:165:52 / :169:67 / :171:71   — همان پیام
```

چون خانوادهٔ `S` در پیکربندی فعلی خاموش است. **اما مراقب باش:** به محضِ انجامِ WP ‏0.9
(روشن‌شدنِ `S`)، این چهار `# noqa` **ناگهان مؤثر** می‌شوند و آن خطوط را برای همیشه
بی‌صدا می‌کنند. پس **ترتیب اجباری** است:

> اول F‑22 را واقعاً رفع کن (bindparams/`quoted_name`)، **بعد** آن `# noqa`ها را پاک کن،
> و **بعد** خانوادهٔ `S` را روشن کن. اگر `ruff check --select RUF100 --fix` را
> **قبل** از رفعِ F‑22 اجرا کنی، این چهار `noqa` حذف می‌شوند و همزمان `S608`
> (در نسخه‌های آیندهٔ ruff که این الگو را بگیرد) یا قاعدهٔ semgrep بی‌پناه می‌ماند.

**و یک تصحیحِ شدت:** عنوانِ «SQL با f‑string» در گزارشِ اصلی بیش از واقعیت ریسک القا می‌کند.
متغیرهای درونِ آن f‑stringها از `sa.inspect()` می‌آیند (نامِ جدول/ستون از خودِ schema)،
**نه از ورودیِ کاربر**. پس این یک **نقصِ الگو/بهداشت** است (Low)، نه یک آسیب‌پذیریِ
قابل‌بهره‌برداری. اولویتش را در `EXECUTION-LOG.md` پایین‌تر از آنچه عنوان القا می‌کند بگذار —
ولی **انجامش بده**، چون مهاجرت‌ها تنها جایی‌اند که SQLِ خامِ بی‌پارامتر در پروژه وجود دارد.
