## ۱) نقشهٔ کلان: دو لوپ + یک دمِ مشترک

```
        ┌─────────────────────────┐   ┌─────────────────────────┐
        │       LOOP-FE           │   │       LOOP-BE           │
        │   UI/UX و فرانت‌اند      │   │       بک‌اند             │
        ├─────────────────────────┤   ├─────────────────────────┤
        │ FE-0 قراردادِ طراحی      │   │ BE-0 SPEC و معیار پذیرش │
        │ FE-1 اسکلت (Vite/TW)    │   │ BE-1 اسکلت (Node)       │
        │ FE-2 پوسته و ناوبری     │   │ BE-2 چهار Adapter       │
        │ FE-3 شش کامپوننت        │   │ BE-3 پایپ‌لاین + SSE     │
        │ FE-4 سه گیتِ طراحی  ◄────┼───┤ BE-4 پایگاه و حافظه     │
        │ FE-5 تأییدِ بصری         │   │ BE-5 گیت‌های بک‌اند      │
        │ FE-6 اتصال به Tauri     │   │ BE-6 بسته‌بندیِ sidecar   │
        └───────────┬─────────────┘   └───────────┬─────────────┘
                    │                             │
                    └──────────┬──────────────────┘
                               ▼
                    ┌─────────────────────────┐
                    │       LOOP-INT          │
                    │  ادغام و تولیدِ نصب‌کننده │
                    ├─────────────────────────┤
                    │ INT-1 پوستهٔ Tauri 2     │
                    │ INT-2 پیوندِ sidecar     │
                    │ INT-3 ساختِ exe / msi    │
                    │ INT-4 موجودیِ مجوزها     │
                    │ INT-5 مدرکِ تحویل        │
                    └─────────────────────────┘
```

**چرا جدا؟** چون گیت‌های FE ماهیتاً *بصری* هستند و گیت‌های BE ماهیتاً *رفتاری*.
قاطی کردن‌شان باعث می‌شود یک اسکرین‌شاتِ بد، کل بیلد را متوقف کند، یا برعکس.

**نقطهٔ تلاقی (FE-4 ◄── BE):** قراردادِ API. تا بک‌اند شکلِ responseها را قطعی نکند،
فرانت با یک **لایهٔ شبیه‌ساز (mock adapter)** کار می‌کند. این یعنی هر دو لوپ می‌توانند
هم‌زمان جلو بروند.

## ۲) سیاستِ خودکاری — فقط دو توقف در کل مسیر

| نوع تصمیم | چه کسی | چرا |

| انتخابِ پالت و تایپوگرافی | 🤖 خودکار | از پایگاه دادهٔ ui-ux-pro-max می‌آید، نه سلیقه |

## ۳) LOOP-BE — گام‌به‌گام

### BE-0 · SPEC
تولید `forge/SPEC.md`: هدف، کاربر، `AC-1..AC-n`، `NG-1..NG-n`، وابستگی‌ها، ریسک‌ها.
هیچ کدی قبل از این نوشته نمی‌شود.

### BE-1 · اسکلت
```
forge/server/
├── package.json          ESM، کم‌وابستگی
├── src/
│   ├── index.ts          سرور HTTP + SSE روی 127.0.0.1
│   ├── config.ts
│   ├── routes/
│   └── core/
└── tests/
```

### BE-2 · چهار Adapter (با امضای یکسان)

```ts
interface Adapter {
  name: string
  health(): Promise<'ready' | 'degraded' | 'missing'>
  // هیچ Adapterی در نبودِ وابستگی‌اش کل اپ را نمی‌ترکاند
}
```

| Adapter | وابستگی | حالتِ degraded |
|---|---|---|
| `JcodeAdapter` | باینری `jcode` | پاسخِ شبیه‌سازی‌شده + هشدار در UI |
| `SoupAdapter` | پایتون ۳٫۱۲ + `soup-ai` | **مسیریابِ داخلی TS** (BM25 + تگ) — هم‌ارزِ منطق Soup |
| `GodmodeAdapter` | فقط فایل | خواندن `skills/*.md` و `agents/*.md` از دیسک |
| `McpClient` | Node ۲۲ + npx | هر سروری که نبود، غیرفععل می‌شود |

> نکتهٔ مهم: `SoupAdapter` **همیشه** یک مسیرِ داخلیِ TS دارد، چون پایتونِ ۳٫۱۲
> روی هر دستگاه ویندوزی تضمین‌شده نیست. این تصمیمِ «قالب A» را ایمن می‌کند.

### BE-3 · پایپ‌لاین
```
درخواست → Soup(انتخاب skill) → Godmode(اگر دستور صدا زده شده) → Jcode(اجرا) → SSE به UI
                                                                      ↓
                                                          بودجهٔ توکن / هزینه
```

### BE-4 · پایگاه
SQLite: نشست‌ها، پیام‌ها، حافظه، مصرف. (هم‌راستا با نقشهٔ راهِ Godmode)

### BE-5 · گیت‌های بک‌اند
`G1 static` · `G2 typecheck` · `G3 lint` · `G4 unit` · `G5 build` · `G6 smoke(health هر ۴ Adapter)`

### BE-6 · بسته‌بندیِ sidecar
ساختِ باینریِ sidecar که Tauri بتواند آن را اجرا کند.

## ۵) LOOP-INT — تا فایل نصبی

### یک واقعیتِ مهم (باید از اول شفاف باشد)

من در این sandbox روی **لینوکس** اجرا می‌شوم. بنابراین:

| خروجی | در sandbox قابل انجام است؟ |
|---|---|
| کل کدِ منبع، تست، بیلدِ لینوکسی، پیش‌نمایش زنده | ✅ بله |
| فایل exe/msi واقعیِ ویندوز | ⚠️ فقط از طریق **GitHub Actions روی runner ویندوزی** |

پس مسیرِ درستِ «تولیدِ خودکارِ exe» این است:
لوپ کد را می‌سازد و پوش می‌دهد → `.github/workflows/build-windows.yml` روی
`windows-latest` اجرا می‌شود → فایل نصب‌کننده به‌عنوان **artifact** تحویل داده می‌شود.
این همان چیزی است که در INT-3 می‌سازیم، و کاملاً خودکار است.

### مراحل
- **INT-1** پوستهٔ Tauri 2 (WebView2 روی ویندوز)
- **INT-2** پیوندِ sidecarِ Node به Tauri
- **INT-3** workflow ساختِ ویندوزی + خروجیِ exe/msi
- **INT-4** موجودیِ مجوزها (MIT/Apache؛ هر قطعهٔ کپی‌شده با سربرگ `SOURCE:`)
- **INT-5** مدرکِ تحویل: لینک artifact + اسکرین‌شات + جدول مجوزها

## ۶) نگهبان‌ها (در هر دو لوپ یکسان)

```
🛡 دستورات مخرب          rm -rf · push --force · reset --hard → توقف
🛡 Placeholder           TODO / not implemented / ... → مانع عبور
🛡 catch خاموش           بدون لاگ یا تلاشِ مجدد → مانع عبور
🛡 سرمنشأ                هر قطعهٔ کپی‌شده سربرگ SOURCE: داشته باشد
🛡 بودجهٔ توکن           سقف برای هر وظیفه
🛡 اندازهٔ باندل         size-limit
```

### طبقه‌بندی خطا و پاسخِ خودکار

| کلاس | پاسخ |
|---|---|
| `BUILD_ERR` `TYPE_ERR` | HEAL تلاش ۱ |
| `TEST_FAIL` | اصلاحِ منطق؛ **حذفِ تست ممنوع** |
| `VISUAL_REG` | HEAL + بازبینیِ توکن‌ها |
| `CTX_BLOAT` | اجبارِ مسیریابی + خلاصه‌سازی |
| `SKILL_CONFLICT` | توقف؛ DESIGN.md مرجع است |
| `HALLUC_API` | راستی‌آزمایی با Context7/DeepWiki؛ حدس ممنوع |
| `SCOPE_CREEP` | revertِ بخشِ خارج از AC |
| `DEPS_DRIFT` | توقف و هماهنگی |

### HEAL (خودترمیمی)
```
تلاش ۱ → وصلهٔ مینیمال
تلاش ۲ → بازگشت + بازخوانیِ فایل‌های درگیر
تلاش ۳ → رویکردِ جایگزین
بعد از ۳ → توقف · revert · گزارشِ علت‌ریشه‌ای + ۳ مسیرِ پیشنهادی
```
هر تلاش روی worktree جدا؛ شکست = حذفِ worktree.

## ۷) اصولِ غیرقابل مذاکره

1. کدِ خارجی بدونِ `SOURCE:` پذیرفته نمی‌شود
2. تستِ قرمز با حذفِ تست سبز نمی‌شود
3. هیچ مرحله‌ای بدونِ مدرکِ قابل مشاهده پاس نمی‌شود
4. DESIGN.md مرجعِ نهاییِ اختلافاتِ بصری است
5. خروج از محدودهٔ AC جاری = revert
6. در نبودِ یک وابستگی، اپ **degraded** می‌شود، نمی‌ترکد
