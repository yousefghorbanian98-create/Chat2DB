## ۰. قرارداد اجرا — بخوان و بپذیر

این سند یک «پروتکل اجرای خودکار» است، نه توصیه. هر ایجنت هوش مصنوعی (Claude Code، Arena، یا هر عامل دیگر) که این سند را در فضای کاری اجرا می‌کند:

1. ابتدا صف/نقشهٔ جاری را بخواند و فقط loopهای فعالِ `READY` را اجرا کند. فاز ۰/ECC پیش‌نیاز فقط loopهایی است که واقعاً به آن وابسته‌اند؛ نبود ابزار، همان loop و وابستگانش را `BLOCKED`/`UNKNOWN` می‌کند، نه کل صف.
2. ترتیب M00 → M17 در این سند تاریخی است و فقط وقتی به‌کار می‌رود که TODO جاری آن بازه را فعال کرده باشد؛ هیچ نقشهٔ آرشیوی خودبه‌خود فعال نیست.
3. ایجنت ECC مشخص‌شده را فقط از راه ابزار واقعاً در دسترس فراخوانی کند؛ خواندن فایل/چک‌لیست یا roleplay اجرای subagent نیست. اگر ECC در دسترس نیست، آن را صریح ثبت کند و loopهای مستقل را ادامه دهد.
4. هر خطا را **دیباگ** کند، هر درس را در Ledger بنویسد و **هرگز اشتباه قبلی را تکرار نکند**.
5. برای نظارت یا تأیید روتین کاربر متوقف نشود: تصمیم محدود، برگشت‌پذیر و درون‌دامنه‌ای را با پیش‌فرض امن بگیرد و در `DECISIONS.md` ثبت کند. تصمیم غیرقابل‌حدس یا گیت واقعیِ بیرونی/ایمنی/حقوقی/امنیتی را حدس نزند؛ فقط loop وابسته را `BLOCKED`/`UNKNOWN` کند و ادامهٔ مستقل را پیش ببرد.
6. هیچ چرخه‌ای بدون عبور از گیت‌های لازم و شاهد متناظر `PASS` نمی‌شود؛ «کلاس جهانی» هدف کیفی است نه تضمین (تعریف معیارها: بخش ۱۰).

### ۳.۱ نصب ابزار (اختیاری و محدود به loop وابسته)

این مثال‌ها **دستور اجرای خودکار نیستند**. فقط اگر یک loop فعال واقعاً به ابزار وابسته باشد، ابتدا اسکریپت/نسخه/اثرهای جانبی را بخوان و `git status` را ثبت کن. هیچ فایل موجود یا untracked را overwrite/delete/ignore نکن؛ اگر نصب امن و غیرمخرب ممکن نیست، همان loop را `BLOCKED`/`UNKNOWN` کن و loopهای مستقل را ادامه بده.

```bash
# نمونهٔ تاریخی — فقط پس از بازرسی و برای وابستگیِ لازم
bash docs/MuscleParadise/finn/install-toolchain.sh ecc
# REA را هم فقط اگر همان loop صریحاً به قابلیت آن نیاز دارد
bash docs/MuscleParadise/finn/install-toolchain.sh rea
```

اسکریپت طبق مستند تاریخی ECC/REA، Node و MCP را در `.finn/`, `.claude/`, `~/toolchain` و `.mcp.json` تغییر می‌دهد؛ این تغییرها ممکن است بر محیط یا فایل‌های موجود اثر بگذارند. نام «idempotent» به‌تنهایی تضمین عدم overwrite/حذف نیست: رفتار واقعی را پیش از اجرا بررسی کن، از نصب غیرضروری یا `@latest` دوری کن و هیچ خروجی نصب/agent را بدون شاهد ادعا نکن.

`install-ecc.sh` قدیمی برای سازگاری باقی است اما **منبع آن فورک قدیمی است؛ اجرا نکن.**

### ۳.۲ روش دستی (legacy؛ بدون کپی کورکورانه)

نمونهٔ `git clone`/`cp -R` قدیمی عمداً به دستور اجرایی تبدیل نمی‌شود: مقصدهای `.finn/ecc/` و `.claude/` ممکن است دادهٔ موجود داشته باشند و `cp -R` می‌تواند آن‌ها را overwrite کند. فقط برای loop وابسته، پس از بررسی مقصد و source، نصب افزایشیِ غیرمخرب را انجام بده؛ اگر نتوان overwrite را منتفی کرد، نصب را انجام نده و همان loop را `BLOCKED`/`UNKNOWN` ثبت کن.

### ۳.۳ روش پلاگین (اختیاری در محیط‌های Claude Code)

این روش برای هر loop یا هر محیطی اجباری نیست. فقط در محیط Claude Code و برای loop وابسته، پس از بررسی منبع/نسخه و تغییرهای مورد انتظار از plugin استفاده کن؛ `npx ...@latest` یا نصب پلاگین خودکار، دستور پیش‌فرض نیست. اگر ابزار در Arena/محیط جاری واقعاً قابل فراخوانی نیست، آن را اجراشده یا subagent ننام.

### ۳.۴ قاعدهٔ فراخوانی/گزارش ایجنت در هر محیط

- **در Claude Code یا orchestrator واقعی:** ایجنت را فقط وقتی subagent بنویس که ابزار واقعاً آن را فراخوانده و خروجی مستقل ثبت شده باشد.
- **در Arena یا چت عمومی:** خواندن `.claude/agents/<name>.md` می‌تواند چک‌لیست/معیار بازبینی باشد، اما نقش‌آفرینی متن‌محور «اجرای subagent» نیست. نتیجه را «چک‌لیست دستی/مرور عامل اصلی» گزارش کن؛ هرگز نام ایجنت اجراشده جعل نکن.
- **فرمان‌ها و اسکیل‌ها:** `/plan`، `/tdd`، `/code-review`، `/e2e` و skillها فقط اگر محیط واقعاً آن‌ها را اجرا کند «اجراشده» محسوب می‌شوند؛ در غیر این صورت معیارهای مرتبط را به‌صورت چک‌لیست دستی و با برچسب دقیق ثبت کن.

## ۵. چرخهٔ درونی FINN — آناتومی هر میکرو-چرخه

هر میکرو-چرخه (M01 … M17) دقیقاً ۴ فاز را طی می‌کند:

```
┌────────────────────────────────────────────────────────────┐
│  F — Forge (ساخت)                                          │
│  planner → architect → tdd-guide → پیاده‌سازی →            │
│  build-error-resolver (تا سبزشدن build/test)               │
├────────────────────────────────────────────────────────────┤
│  I — Inspect (بازبینی)                                     │
│  code-reviewer (چک‌لیست کیفیت) → اجرای کامل تست‌ها →       │
│  e2e-runner (مسیرهای حیاتی)                                │
├────────────────────────────────────────────────────────────┤
│  N — Normalize (نرمال‌سازی)                                │
│  refactor-cleaner (حذف تکرار/کد مرده) → security-reviewer   │
│  (OWASP + bandit/pip-audit) → build-error-resolver نهایی    │
├────────────────────────────────────────────────────────────┤
│  N — Next (گام بعد)                                        │
│  doc-updater (مستندات + CHANGELOG) → به‌روزرسانی LEDGER/    │
│  STATE/REGRESSIONS → commit → چرخهٔ بعد                    │
└────────────────────────────────────────────────────────────┘
```

### گیت‌های پایان هر میکرو-چرخه (Definition of Done) — همه اجباری

1. ✅ build بدون خطا (`pytest` / `flutter test` / `npm run build` بسته به لایه)
2. ✅ پوشش تست بک‌اند ≥ ۷۰٪ (طبق لایهٔ ۱۴ طرح) — بدون کاهش نسبت به چرخهٔ قبل
3. ✅ لینت و فرمت تمیز (`ruff`، `eslint`، `dart analyze`)

## ۸. پروتکل دیباگ و شکست (در هر مرحله)

```
خطا/شکست تست
  │
  ├─ تلاش ۱: build-error-resolver → رفع → اجرای کامل تست‌ها
  │     ├─ سبز؟ → ثبت در LEDGER (اگر درس جدیدی داشت) → ادامه
  │     └─ قرمز؟ ↓
  ├─ تلاش ۲: بازتولید خطا (minimal repro) → ریشه‌یابی → رفع → تست + رگریشن جدید
  │     ├─ سبز؟ → ادامه
  │     └─ قرمز؟ ↓
  ├─ تلاش ۳: محدودکردن دامنه (کوچک‌ترین زیربخش) → رفع → تست
  │     ├─ سبز؟ → ادامه
  │     └─ قرمز؟ ↓
  └─ بعد از ۳ شکست: همان loop را `FAIL`/`BLOCKED` ثبت کن؛ آثار workspace را حفظ کن
        → ثبت کامل ماجرا در LEDGER + DECISIONS و نام‌گذاری وابستگی‌ها
        → از `git reset --hard`, `git clean` یا overwrite برای rollback استفاده نکن
        → loop مستقل بعدی را ادامه بده؛ loop شکست‌خورده فقط با راهکار تازه و گیت‌هایش بازگشایی می‌شود
```

- هر خطا در `LEDGER.md` با ستون «قانون جدید (هرگز…)» ثبت می‌شود.
- خطاهای محیطی (قطع شبکه، سرویس در دسترس نیست): ۳ بار تلاش مجدد با تأخیر، سپس مسیر جایگزین طرح (جدول پیوست الف) و ثبت تصمیم.

## ۹. موتور ضدتکرار (Anti-Repetition Engine)

1. **پیش از ساخت:** Grep/Glob برای نام‌ها و مفاهیم مشابه؛ اگر ماژول/تابع مشابهی هست، افزونه بساز، کپی نکن.
2. **پیش از رفع باگ:** جست‌وجوی LEDGER برای باگ مشابه قبلی — اگر هست، «قانون هرگز» همان را اعمال کن.
3. **پس از رفع باگ:** تست رگریشن در `REGRESSIONS.md` + اجرایش در همهٔ چرخه‌های بعد.
4. **درس تکراری ممنوع:** اگر همان درس دوباره ثبت شد، یعنی لوپ خطا کرده → چرخه قبول نیست تا یک «قانون اجرایی» (مثلاً تست، هوک، یا lint rule) آن را مکانیکی کند — نه فقط تذکر متنی.
5. **کامیت‌ها:** هر commit فقط مربوط به یک چرخه؛ تاریخچه تمیز = قابلیت rollback واقعی.

## ۱۱. پایان و توقفِ محدود به loop

**پایان موفق تاریخی:** M00 تا M17 فقط اگر در صف جاری صریحاً فعال باشند، با گیت‌های بخش ۵ و `finn/FINAL_REPORT.md` دارای شواهد بسته می‌شوند. گزارش آمادگی انتشار، مجوز release/deploy نیست.

**مانع یا تناقض:** پس از تلاش‌های محدود و مسیر جایگزینِ امن، مانع واقعیِ بیرونی، نبود ابزار/دستگاه، یا تناقضی که بدون حدس حل نمی‌شود، فقط loop وابسته و وابستگانش را `BLOCKED`/`UNKNOWN` می‌کند. شواهد و مسیر بازتولید ثبت شود؛ گیت دور زده یا انتخاب حقوقی/ایمنی/مالی حدس زده نشود؛ loopهای مستقلِ `READY` ادامه یابند.

**پایان کل صف:** فقط وقتی هیچ loop مستقلِ فعال و مجازِ `READY` باقی نمانده باشد، یا مانع ایمنی/یکپارچگیِ سراسری ادامهٔ هرگونه کار را ناامن کند. در آن صورت گزارش وضعیت و موانع تهیه می‌شود؛ از کاربر برای نظارت روتین سؤال نمی‌شود. گیت‌های قرمز، تست‌های اجرا‌نشده یا `UNKNOWN` هرگز به `PASS` تبدیل نمی‌شوند.
