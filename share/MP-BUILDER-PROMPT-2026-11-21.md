````
# ۱۲ قانون غیرقابل مذاکره

1. **اول بازتولید، بعد اصلاح.** پیش از دست‌زدن به هر یافته، آن را با «شاهدِ پذیرش» یا فرمانِ
   §۱۰ پرونده بازتولید کن و خروجی را ذخیره کن. اگر بازتولید نشد، آن را
   `NOT-REPRODUCED` علامت بزن، شواهدت را بنویس و **سراغ بعدی برو** — هیچ‌وقت کور اصلاح نکن.
2. **هر یافته = یک PR جدا.** هیچ‌وقت چند یافتهٔ نامرتبط را در یک commit نریز.
3. **هر PR باید چهار چیز داشته باشد:** پچ + تستِ رگرسیون + شاهدِ اجراییِ عددی (قبل/بعد) +
   به‌روزرسانیِ سند مربوطه. بدون این چهار مورد، PR کامل نیست.
4. **هیچ تستِ پاسی را برای سبز شدنِ تغییرت ضعیف نکن** (حذف/`skip`/شل‌کردن assert ممنوع).
   اگر تستی واقعاً اشتباه است، در یک commit جدا اصلاحش کن و دلیلش را بنویس.
5. **۲۷ خاصیت سالم را نشکن.** پس از هر فاز، «گیتِ سلامت» (بخش «پروتکل تأیید») را اجرا کن.
   به‌ویژه: صفر drift قرارداد، صفر `5xx` در ماتریس، جداسازی member‑scope (۰/۱۶)،
   سخت‌گیری JWT، یک‌بارمصرفی OTP، idempotency پرداخت، هدرهای امنیتی،
   نبودِ `dangerouslySetInnerHTML`.
6. **۱۲ یافتهٔ کاذبِ رد‌شده را دوباره باز نکن** (§۹ گزارش): نبودِ CSP، «۴۱ `print()` در کلاینت»،
   «۷۵ دکمهٔ بی‌سیم»، نشت session در اسکریپت‌ها، «StreamingResponse در AI/chat»،
   «صفحه‌های Analytics/Login/Assessment مرده‌اند»، «`fetchOrderReceipt`/`markOrderStatus` مرده‌اند».
   این‌ها با اجرا رد شده‌اند؛ وقت گذاشتن روی آن‌ها اتلاف است.
7. **ابزارها فقط رایگان و بازمتن.** ابزارهای AGPL/GPL/LGPL (semgrep CLI, repowise, loki, k6,
   trufflehog, renovate, sonarqube, hadolint) **فقط به‌عنوان ابزار توسعه/CI** مجازند و هرگز
   نباید داخل artifact توزیعی (APK/image/کد محصول) بروند — چون MP مجوز اختصاصی دارد.
   **هرگز استفاده نکن:** `dart-code-checker/dart-code-metrics` (NOASSERTION + آرشیوشده)،
   `doyensec/electronegativity` (آرشیوشده).
8. **دو محیط مجازی را قاطی نکن.** `venv` = وابستگی‌های اپ؛ `venv-audit` = ابزارهای ممیزی.
   semgrep در محیط اپ کرش می‌کند (تضاد پینِ otel با fastapi).
9. **هیچ دادهٔ واقعیِ عضو/مالی نساز و استفاده نکن.** همهٔ داده‌ها مصنوعی
   (الگوی `0912…`/`0913…` از seed خودِ پروژه).
10. **GitHub Actions را به SHA پین کن.** امروز هر ۴۲ ارجاع `uses:` با tag متحرک‌اند و
    صفر مورد SHA‑pin دارد؛ هر workflow جدید یا اصلاح‌شده باید با `pin-github-action` پین شود.
11. **پیش از هر فاز، `git status --porcelain` را صفر کن** و مطمئن شو چیزی از فاز قبل جا نیفتاده.
    اگر از ابزارِ جهش (mutmut) استفاده کردی، حتماً `git checkout -- <file>` را بعد از هر جهش بزن.
12. **صبر و ترتیب.** فازها را به‌ترتیب اجرا کن؛ اگر گیتِ یک فاز قرمز شد، **همان‌جا بایست**،
    علت را ریشه‌یابی کن و گزارش بده — رد شدن از گیتِ قرمز ممنوع.

   «عضو هست ولی داده ندارد» (۲۰۰ تهی) تفاوت بگذارد؟ (پیشنهاد: بله — این دقیقاً همان چیزی است

# قراردادِ خروجیِ هر بستهٔ کاری (WP)

هر WP یک PR و یک رکورد در `EXECUTION-LOG.md` با این قالب:

```
## WP <n> · F‑xx · <عنوان کوتاه>
- بازتولید: <فرمان> ⇒ <خروجی واقعی قبل از اصلاح>
- ریشه: <file:line> + <توضیح یک‌خطی>
- تغییرات: <فهرست فایل‌ها> (تعداد خط +/-)
- تست‌های اضافه: <نام‌ها> — <تعداد>
- شاهدِ بعد از اصلاح: <فرمان> ⇒ <خروجی واقعی>
- گیت عددی: <آستانهٔ مقرر> ⇒ PASS/FAIL
- مستنداتِ به‌روز‌شده: <فایل‌ها>
- گیت سلامتِ پس از فاز: PASS
- ریسک/بازگشتِ احتمالی: …
- تصمیمِ مرتبط: D‑n (اگر دارد)

**بدون «انجام شد»ِ بدون شاهد.** هر ادعا باید یک خروجیِ واقعیِ چسبانده‌شده داشته باشد.

1. هر ۲۷ یافته یا `FIXED` با شاهدِ عددی، یا `DEFERRED` با رکوردِ D‑n و دلیلِ صریح.

3. همهٔ گیت‌های عددیِ جدول‌های بالا سبز.
4. CI شامل این‌ها باشد و سبز: pytest + پوششِ تفکیکی، `tsc`، vitest، **eslint (۰ error)**،
   ruff، semgrep با `semgrep-mp.yml` (۰ یافته)، آزمونِ قراردادِ ماتریس ۱۶۳×۷،
   آزمونِ شناسه/پاکت/مبلغ (§3.5)، آزمونِ جهش روی ماژول‌های پولی (≥۸۰٪)،
   گیتِ حجمِ لاگ و بارِ پله‌ای (شبانه)، Actions پین‌شده به SHA.
5. مستندات اصلاح شده باشد: `README` (اعداد ۱۴۱/۱۶۳ و پوششِ واقعی با دامنهٔ صریح)،
   `DEPLOYMENT.md` و `OPS-RUNBOOK.md` (XFF، حساب ظرفیت، pragmaها)،
   `PROJECT-HANDOFF.md` (ماژول‌ها، محدودیت‌های shop، پیش‌نیازِ پروندهٔ عضو).
6. `BASELINE.md` در برابر `FINAL.md`: جدولِ قبل/بعد برای **همهٔ** اعدادِ کلیدی.
7. یک اجرای «اورلود» نهایی: ۲۰۰ کلاینت همزمان + پلهٔ ۸۰ ورکر + ۳۲٬۰۰۰ فراخوانیِ RBAC،
````
