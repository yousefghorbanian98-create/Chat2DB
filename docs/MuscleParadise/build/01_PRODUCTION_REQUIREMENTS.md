# 01 — الزامات تولید (Production Requirements)

> «آماده برای تولید» یعنی چه؟ این سند آن را به اعداد قابل‌سنجش تبدیل می‌کند.
> هر ردیفی که ✅ ندارد، هنوز حق ندارد در Release Notes به‌عنوان «کامل» بیاید.

## 1. پرسونا و بارِ واقعی

| پرسونا | تعداد | الگوی استفاده |
|--------|-------|----------------|
| مالک/مربی (Studio) | ۱ تا ۳ کاربر همزمان | کل روز باز، داشبورد + ثبت آنالیز |
| پذیرش (Reception) | ۱ | پیک ۱۷:۰۰–۲۱:۰۰، ثبت پرداخت/تمدید |
| کیوسک | ۱ دستگاه | اسکن QR، هر ۵–۱۵ ثانیه یک تراکنش در پیک |
| ورزشکار (Client) | **۳۰۰ تا ۲۰۰۰ عضو** | موبایل، چند بار در هفته |

**بار طراحی هدف:** ۵۰ درخواست در ثانیه در پیک روی یک PC معمولی باشگاه
(Core i3، ۸GB RAM، SSD، بدون GPU). SQLite در حالت WAL برای این بار **کافی است**؛
معیار مهاجرت به Postgres در سند ۰۲ §۸ آمده.

## 3. الزامات غیرکارکردی (NFR) با عدد

### 3.1 عملکرد

| سنجه | هدف | وضعیت فعلی |
|------|-----|-------------|
| P95 پاسخ API خواندنی | < 120 ms روی PC هدف | اندازه‌گیری نشده — **بدهی** |
| P95 پاسخ API نوشتنی | < 300 ms | اندازه‌گیری نشده |
| LCP صفحهٔ ورود | < 1.8 s روی LAN | اندازه‌گیری نشده (مرورگر در CI نیست) |
| باندل اولیه JS | < 250 kB gzip | ✅ 6.24 kB entry + 108 kB vendor |
| زمان بوت سرد هسته | < 3 s | ~1.5 s (مشاهده‌شده) |
| اسکن تا ثبت حضور | < 800 ms | اندازه‌گیری نشده |

**اقدام لازم:** یک تست بار (`locust` یا `k6`) و یک Lighthouse CI روی GitHub Actions
(که مرورگر دارد، برخلاف این سندباکس). بدون این، سه ردیف بالا برای همیشه «نامعلوم» می‌مانند.

### 3.2 دسترس‌پذیری (Availability)

| سنجه | هدف |
|------|-----|
| در دسترس بودن هسته در ساعات کاری | ۹۹.۵٪ ماهانه (≈ ۲ ساعت خرابی مجاز) |
| RPO (حداکثر داده از دست رفته) | ۱ ساعت — پشتیبان خودکار ساعتی |
| RTO (زمان بازیابی) | ۱۵ دقیقه از فایل پشتیبان رمزشده |
| کارکرد آفلاین کامل | **اجباری** — قطع اینترنت نباید هیچ عملیاتی را بشکند |

### 3.3 دسترس‌پذیری برای معلولان (a11y)

- **WCAG 2.2 سطح AA** به‌عنوان دروازه، نه آرزو.
- کنتراست متن ≥ 4.5:1 (توکن‌های فعلی باید با `axe` سنجیده شوند).
- کل جریان‌های حیاتی (ورود، اسکن، ثبت ست) فقط با کیبورد قابل انجام.
- `prefers-reduced-motion` محترم شمرده شود ✅ (پیاده شده و تست دارد).
- هدف لمسی ≥ 44×44 px برای کیوسک و موبایل.
- **ابزار دروازه:** `vitest-axe` در تست کامپوننت + `@axe-core/cli` در CI.

### 3.4 بین‌المللی‌سازی

- فارسی زبان اول، `dir="rtl"` در سطح سند.
- تاریخ **جلالی** در تمام سطوح UI ✅ (۹ لنگر تست‌شده).
- پول: **ریال** با جداکنندهٔ سه‌رقمی فارسی.
- اعداد: ارقام فارسی در نمایش، ارقام لاتین در ورودی و ذخیره.
- انگلیسی به‌عنوان زبان دوم — **نیازمند استخراج رشته‌ها** (اکنون هارد-کد است).

### 3.5 قابلیت مشاهده (Observability)

| لایه | الزام | وضعیت |
|------|-------|--------|
| Request ID روی هر پاسخ | ✅ پیاده شده |
| لاگ ساخت‌یافته JSON | ❌ اکنون متن ساده |
| متریک `/metrics` (Prometheus) | ❌ نیست |
| ردیابی خطا با استک محلی | ⚠️ `ERRORS.log` دستی است |
| صفحهٔ سلامت `/health` | ✅ |

## 4. الزامات انطباق و داده

| موضوع | قانون |
|-------|-------|
| PHI (مصدومیت، پوست‌چین، وزن) | هرگز از LAN باشگاه خارج نمی‌شود مگر با صادرات صریح مالک |
| n8n bridge | فقط شناسه و رویداد؛ **هیچ نام، تلفن یا داده سلامتی** |
| حق حذف عضو | حذف نرم + ابزار «پاک‌سازی سخت» با تأیید دو مرحله‌ای مالک |
| نگهداری پشتیبان | ۳۰ نسخهٔ آخر، رمزشده با Fernet، کلید روی همان ماشین |
| رضایت‌نامه | امضای دیجیتال قبل از اولین آنالیز بدنی — **هنوز اجرا نمی‌شود** |
| زیر ۱۸ سال | `guardian_consent` اجباری قبل از فعال‌سازی برنامه |

## 5. دروازه‌های انتشار (Release Gates)

هیچ تگی بدون سبز بودن **هر ۹ ردیف** ساخته نمی‌شود:

```
1. pytest                       exit 0, coverage ≥ 85%   (اکنون 90.9% ✅)
2. npm run gate                 exit 0                    (✅)
3. pip-audit / npm audit        0 آسیب‌پذیری high/critical (❌ اجرا نمی‌شود)
4. مجوزها                        هیچ GPL/AGPL در باینری     (⚠️ دستی)
5. Lighthouse a11y + perf       ≥ 90                      (❌)
6. تست بار                       P95 < اهداف §3.1          (❌)
7. مهاجرت DB                     up + down روی DB واقعی     (⚠️ فقط up)
8. دود تست نصب‌کننده             نصب و اجرای واقعی ویندوز    (⚠️)
9. CHANGELOG                     ورودی با عدد اندازه‌گیری‌شده (✅)
```

**۵ دروازه از ۹ هنوز وجود ندارند.** اولویت اول کاری، ساختن همان ۵ تاست (سند ۱۲، هفتهٔ ۱–۲).

## 6. معیار خروج v1.0 GA

محصول وقتی GA است که یک مربی غریبه، بدون کمک، بتواند:

1. نصب‌کننده را اجرا کند و در < ۵ دقیقه به داشبورد برسد؛
2. ۵۰ عضو را از فایل CSV وارد کند؛
3. یک آنالیز JP7 بگیرد و PDF فارسی سالم چاپ کند؛
4. برنامه‌ای بسازد که یک مصدومیت زانو را **واقعاً** فیلتر کند؛
5. ورزشکار با موبایل QR بزند و پرداختش را ببیند؛
6. برق را بکشد، دوباره بزند، و **هیچ داده‌ای نرفته باشد**؛
7. پشتیبان بگیرد، روی PC دیگری بازیابی کند، و همان اعداد را ببیند.

هر هفت مورد باید در یک جلسهٔ ضبط‌شدهٔ تست کاربری واقعی اثبات شود — نه در تست خودکار.
