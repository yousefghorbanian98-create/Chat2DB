## 2. آنچه درست پیاده شده ✅

### 2.1 هش کردن راز
```
PBKDF2-HMAC-SHA256 · 200,000 تکرار · نمک ۱۶ بایتی تصادفی
قالب: algo$iterations$salt$digest
```
تعداد تکرار مطابق توصیهٔ فعلی OWASP است. قالب، تکرارها را ذخیره می‌کند پس
افزایش آیندهٔ آن بدون شکستن هش‌های قدیمی ممکن است — طراحی درست.

**بهبود پیشنهادی:** اگر روزی وابستگی مجاز شد، `argon2id` بهتر از PBKDF2 است
(مقاوم به GPU). ولی PBKDF2 با ۲۰۰k برای این تهدید کافی است.

### 2.2 QR امضاشده
HMAC-SHA256 روی محتوا + زمان انقضا. عکس گرفتن از QR بعد از انقضا بی‌فایده است.
**نکتهٔ باقی‌مانده:** بازپخش *درون* پنجرهٔ اعتبار هنوز ممکن است. اگر پنجره ۳۰ ثانیه است،
کسی می‌تواند در همان ۳۰ ثانیه از عکس استفاده کند. حل: ذخیرهٔ `jti` هر QR مصرف‌شده.

### 2.3 عدم شمارش کاربر
هر سه حالت (کاربر ناموجود، غیرفعال، PIN غلط) پیام و کد یکسان می‌دهند.
همچنین مربی روی عضو تخصیص‌نیافته **۴۰۴** می‌گیرد نه ۴۰۳ — تا وجود آن عضو فاش نشود.
این جزئیات، نشانهٔ کار حرفه‌ای است.

### 2.4 ماسک میدانی
`core/field_mask.py` با سه تابع (`mask_member_row`, `mask_assessment_row`,
`mask_nutrition_row`) پاکت `payload` و `clinician_note` را حذف می‌کند و `pin_hash`
هرگز در ستون‌های خواندنی نیست.

### 2.5 امنیت Electron
`contextIsolation: true`، `nodeIntegration: false` ✅ — پایه‌های درست.
**اضافه کنید:** `sandbox: true` (کامنت ادعایش را می‌کند، کد ست نمی‌کند)، و یک هندلر
`setWindowOpenHandler` که هر ناوبری بیرونی را رد کند.

### 2.6 انضباط لایسنس
`python-bidi` (LGPL-3.0) رد و بازنویسی شد. `exercises.source_license` مجوز هر
حرکت را حمل می‌کند. `NOTICES.md` نگهداری می‌شود.

## 3. 🔴 هشت شکاف امنیتی — به ترتیب فوریت

### P0 — قبل از هر انتشار عمومی

**1. محدودیت نرخ روی احراز هویت.**
PIN چهاررقمی = ۱۰٬۰۰۰ حالت. بدون قفل، روی LAN چند ثانیه کار دارد.
```
۵ خطای متوالی  → ۳۰ ثانیه قفل
۱۰ خطا         → ۵ دقیقه
۲۰ خطا         → قفل تا باز کردن دستی مالک + ثبت در audit_log
کلید: (gym_id, username|membership_code, client_ip)
```

**2. سیاست حداقلی PIN.**
اکنون PIN `1234` مجاز است (و در دمو استفاده شده). ممنوع کنید: تکراری (`1111`)،
متوالی (`1234`)، و ۲۰ PIN رایج. برای کارکنان: رمز عبور ≥ ۱۰ کاراکتر، نه PIN.

**3. ابطال توکن.**
جدول `revoked_tokens(jti, exp)` + بررسی در `auth/deps.py` + دکمهٔ «خروج از همهٔ دستگاه‌ها».

**4. `audit_log` واقعاً بنویسد.**
بدون آن، هیچ ادعای انکارناپذیری وجود ندارد. حداقل رویدادها در سند ۰۲ §۵.

### P1 — قبل از v1.0

**5. TLS روی LAN.**
اکنون HTTP ساده. یک گواهی خودامضا که نصب‌کننده تولید و در Trust Store ویندوز نصب کند،
و اپ اندروید آن را pin کند. یا حداقل `network_security_config.xml` که cleartext را
فقط به `192.168.0.0/16` و `10.0.0.0/8` محدود کند.

**6. هدرهای امنیتی HTTP.**
```
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none';
                         frame-ancestors 'none'; base-uri 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(self), microphone=(), geolocation=()
```
`camera=(self)` لازم است چون اسکن QR دوربین می‌خواهد.

**7. سهمیه و محدودیت اندازه.**
حداکثر اندازهٔ بدنهٔ درخواست (۲ MB)، حداکثر عکس پیشرفت (۵ MB)، سهمیهٔ کل هر عضو،
و بررسی فضای دیسک قبل از نوشتن.

**8. اسکن وابستگی در CI.**
```yaml
- run: pip-audit -r mp-app/backend/requirements.txt --strict
- run: npm audit --audit-level=high
```
اکنون هیچ‌کدام اجرا نمی‌شوند. یک CVE در FastAPI یا Vite می‌تواند ماه‌ها ناشناخته بماند.

## 4. حریم خصوصی — قواعد سختِ دادهٔ سلامتی

| قاعده | اجرا |
|-------|------|
| PHI هرگز از LAN خارج نمی‌شود مگر با صادرات صریح مالک | ✅ معماری local-first |
| n8n فقط شناسه و رویداد می‌گیرد | ✅ — **ولی تست فهرست سفید ندارد** |
| یادداشت بالینی ≠ یادداشت قابل‌رؤیت عضو | ✅ دو ستون جدا |
| حق حذف: پاک‌سازی سخت با تأیید دو مرحله‌ای | ❌ فقط حذف نرم |
| حداقل‌سازی: اثر انگشت = فقط قالب/هش | ✅ در طراحی (پیاده نشده) |
| رضایت‌نامه قبل از اولین آنالیز | ❌ جدول هست، اجبار نیست |
| زیر ۱۸ سال: `guardian_consent` اجباری | ❌ ستون هست، اجبار نیست |

**دو مورد آخر ریسک حقوقی واقعی هستند.** آنالیز بدنی روی نوجوان بدون رضایت ولی،
در بسیاری از حوزه‌های قضایی مشکل‌ساز است. یک بررسی سمت سرور که بدون رضایت امضاشده،
`POST /assessments` را با ۴۲۲ رد کند، کار یک ساعته است.

## 5. پشتیبان و بازیابی

✅ رمزنگاری Fernet، کلید محلی.
🔴 شکاف‌ها:
- زمان‌بندی خودکار وجود ندارد → RPO ۱ ساعته تضمین نشده؛
- از `VACUUM INTO` استفاده نمی‌شود → ریسک پشتیبان ناسازگار؛
- **تست بازیابی خودکار نیست** — پشتیبانی که بازیابی‌اش آزموده نشده، پشتیبان نیست.
  یک تست CI: DB بساز → داده بریز → پشتیبان بگیر → پاک کن → بازیابی کن → checksum مقایسه کن.
- کلید پشتیبان کجا نگهداری می‌شود؟ اگر کنار خود پشتیبان روی همان دیسک باشد،
  در برابر سرقت PC بی‌فایده است. باید عبارت‌عبور مالک آن را بپوشاند.

## 6. اعتبارسنجی امنیتی — چه کسی می‌سنجد

سه لایه، هر سه لازم:

1. **خودکار در CI:** `pip-audit`, `npm audit`, `bandit -r app/`, `semgrep --config=auto`.
2. **تست‌های امنیتی به‌عنوان تست عادی:** برای هر مسیر، یک تست ۴۰۱ و یک ۴۰۳.
   (بخشی موجود است — به همهٔ ۴۹ مسیر تعمیم دهید.)
3. **بازبینی دستی قبل از GA:** یک چک‌لیست OWASP ASVS سطح ۲، امضاشده و تاریخ‌دار.

اگر ابزار تجاری مثل Strix در دسترس است، آن را **بعد از** این سه لایه بگذارید، نه به‌جایشان.
اسکنر خودکار جایگزین محدودیت نرخِ ننوشته نمی‌شود.
